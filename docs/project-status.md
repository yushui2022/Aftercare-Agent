关键风险：恢复演练通过只说明 dump 可恢复，不说明恢复后外部世界与数据库一致，因此必须结合 `reconcile`；`reconcile` 的安全边界仍是环境参数，调小会增加漏报风险。备份、演练记录和 WAL 当前没有异地加密副本，`--apply` 不应在此之前自动清理唯一副本。`wal` 只描述目录当前内容，没有 `--dsn` 时不能证明归档器仍在推进。真实 IdP 中 `grant:admin`、`grant:read` 和 `review:override` 都是高敏权限；控制面清单不能替代数据面 CaseGrant。连接池默认值不能当容量承诺，池化连接也不能遗留会话状态。模型策略切换尚未版本化，当前 override 只允许单调增加预算或 deadline，并且必须绑定 checkpoint 版本和审计记录。

第二刀之后新增两条同源风险：(1) `status` 判的是“目录里的记录与预算的关系”——它读 dump 的字节数与 SHA-256 字段，但不重算 dump 的内容，所以记录可读而 dump 已被替换或损坏时 `status` 仍可能报通过，**`verify` 才是完整性判据，两者不能互相替代**；(2) 演练记录与 dump 写在同一目录、同一个可写身份下，能改 dump 的人也能改记录，因此它防的是“忘记演练”和“演练静默失败”，不防内部人伪造演练；异地副本与备份加密落地前不要把 `status` 的通过当成合规证据。另外“未配置预算 ≠ 已满足”必须保持——任何为了“让面板变绿”而给出默认 RPO/RTO 的改动，都会把一个未决的部署决策伪装成通过。D-02 原有三条风险仍然成立。
工具执行面剩余风险：(1) 持久路由、operator `route_reason` 和预算/deadline override 已落地，但策略切换、生产预算和定价入口仍未完成；(2) 沙箱 tier 只按工具名映射，执行队列 priority 没有 class 生产者，队列排序与审批阈值仍未按层生效；(3) 订单、物流和买方陈述已进入账本，EGM 写入与撤回传播均有持久收据，标准化来源事件也有认证边界和本机 PostgreSQL 重放证据，但供应商原生验签、更宽恢复矩阵和目标环境复跑仍未完成；(4) `SandboxedToolExecutor` 的 `request_key` 含 Worker 身份，换 owner 的恢复会开新沙箱，这是允许恢复的资源代价，不是业务副作用重放；(5) `aftercare-rls harden` 会让未来带租户表的 owner 也受 RLS 约束，后续迁移若包含数据回填，必须显式设计 migration/owner 的受控上下文或独立运维权限，不能临时给 runtime 加 `BYPASSRLS`。
