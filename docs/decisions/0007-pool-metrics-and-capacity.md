# ADR-0007：池指标与每进程 `max_size` 的测量定标

状态：接受，D-03 实施中。本 ADR 收口 [ADR-0006](0006-bounded-connection-pool.md) 明确留下的两条
未完成项——池指标接入观测、D-03 压测为 `max_size` 定标——并把"怎么算定标了"写清楚。它不替代任何
既有决策：ADR-0002 的嵌入式 EGM、ADR-0003/0004/0005 的授权边界、ADR-0006 的池语义继续有效。

## 背景

ADR-0006 做了两件事：把连接池启用起来，并把 `min 1 / max 8 / 超时 5 s` 明确写成**默认值而不是
容量结论**。它同时承认两个洞：池指标（等待数、超时数、连接数）没进观测；`max_size` 没有测量依据。

本轮把这两件事补上，并且在测量中发现一个比 `max_size` 更要紧的事实。

## 决策

1. **`Database.stats()` 是池健康的唯一读取口**，返回冻结的 `PoolStats` 快照。快照只含整数：池的
   最小/上限/当前连接数、空闲槽、等待者数、累计请求数、排队数、请求错误数、累计排队毫秒、累计
   建连数与建连失败数、丢失连接数。没有任何字段能装下租户、工单、语句或 DSN，所以快照可以安全地
   当指标发布；`Database.direct()` 与已关闭的池返回 `None`。
2. **指标名与标签是闭集**：`aftercare.db.pool.*`，一次快照发布 6 个 gauge（`connections.min/max/
   size/available/in_use`、`requests.waiting`）与 7 个 counter（`connections.opened/errors/lost`、
   `requests.total/queued/errors/wait_ms`）。唯一属性是 `component`（`api`、`worker`）。池是全进程
   共享的，用租户或工单给它打标签既解释不了谁在等，又会炸基数。
3. **`PoolStatsSampler` 是唯一发布者**：默认每 10 s 一次，`AFTERCARE_POOL_METRICS=0` 关闭，
   `AFTERCARE_POOL_METRICS_INTERVAL_SECONDS` 改间隔；启动时立刻采一次，所以一次性的 CLI 进程也
   报告它自己的池。**采样失败只停线程、不失败进程**——这和租约心跳正好相反：心跳读不到数据库就不能
   继续证明持久权，而丢一个诊断不该让业务失败。
4. **默认 sink 是标准库日志**（`LoggingMetrics`：一行 JSON），OTel bridge 是可选类，导出器、采样与
   留存仍属 C-03。这样池健康在没有任何供应商依赖的情况下可观测，接导出器时不用改采样器。
5. **定标必须来自 `aftercare-capacity` 的实测 sweep**。探针在一个真实 PostgreSQL 上按
   steady / burst / wake（集中唤醒）三种形状、对一组 `max_size` 各跑一遍，报成功数、拒绝数、延迟
   分位、池高水位、累计排队时间、建连数与墙钟时间，最后给出在给定 p95 预算下最小的达标尺寸。
   公布容量数字必须同时公布版本、工作负载、失败率、延迟和资源成本；样例参数不是 SLA。
6. **定标口径**：`max_size` 要覆盖"这个进程必须同时承载的工作单元数"，`min_size` 决定突发时要不要
   付握手。只有 sweep 在目标工作负载与目标预算下给出该尺寸，才调大默认值。
7. **探针只测池**：不跑 Agent、不调用模型、不碰供应商，也不为了数字放宽事务边界（不加长事务、
   不自动重试、不让 Repository 持有连接）。

## 本机实测（2026-09-15，临时真实 PostgreSQL 16.13，CPython 3.13.15）

工作负载：16 并发、每个工作单元一次 10 ms 短事务、p95 预算 50 ms。报告原文见
[容量报告](../capacity/README.md)。

| 配置 | 结论 | 关键数字 |
|---|---|---|
| 懒增长 `min_size=1`，sweep 1–32 | **没有尺寸达标** | steady 的 p95 在 1/2/4/8/16/32 上是 262/130/125/168/128/124 ms；`max_size` 从 8 提到 32 时 in_use 峰值只从 8 升到 10（本机建连 p50 约 115 ms，池一次只长一条） |
| 预热 `min_size=16`，sweep 16/32 | **`max_size=16` 达标，32 无差别** | p95 31.3–39.1 ms，池排队时间 **0 ms**，in_use 峰值 16；`max_size=32` 的 p95 31.6–38.6 ms |
| 纯开销对照（单元 = `SELECT 1`） | 1/8/16 都达标 25 ms | 16 并发下 p50 2.7–8.6 ms；同一个池，换成重工作负载就判然不同 |

**结论：突发并发先撞上的是握手与懒增长，不是上限。** 提高 `max_size` 而不预热，等于把预算花在
一条 borrow 拿不到就立刻新建连接的路径上；预热到并发量之后，再加上限买不到任何东西。

因此本轮**不改默认值**：API `min 1 / max 8`、Worker `min 1 / max 4` 保持不变，它们是"按并发有界"
的默认，不是容量结论。要改默认值需要目标部署的工作负载与预算，本机单机数据不能替代。

## 后果

- 每个进程多一个采样线程（默认 10 s 一次 `get_stats()`，不发 SQL），日志 sink 每 10 s 一行 JSON。
- `in_use_high_water` / `waiting_high_water` 是**采样值**（默认 5 ms 一次），比采样间隔短的工作单元
  可能采不到峰值；报告同时给出 `watcher_samples`，读的人知道峰值有多可信。
- 探针的工作单元由 Python 线程发起：本机 16 线程 + 10 ms 单元的下限约 29 ms/单元，所以跨主机比较
  要看相对值，不要拿绝对毫秒当跨环境常数。
- 只在**一台开发机**上测过。生产、CI、容器内的容量结论仍然未定；这份数字的用途是固定方法与口径，
  不是宣布一个 SLA。
- 已补齐 Worker 的业务队列诊断：`aftercare.queue.runnable_runs` 与
  `aftercare.queue.oldest_age_seconds` 使用短事务只读快照，唯一标签仍是
  `component`，不会领取任务或改变租约；`AFTERCARE_QUEUE_METRICS=0` 可关闭。
- 仍未完成：OTel 导出器/采样/留存（C-03）、在容器与 CI 环境复跑同一条 sweep，以及目标
  环境的队列年龄告警阈值与容量结论。
