# 从 Demo 到企业级：一个跨境电商售后 Agent 的并发、沙箱与故障恢复设计

> 本文是一套参考架构，不是某家公司的生产系统复盘。产品与协议资料核查于 2026 年 9 月 6 日；文中的容量、超时和业务数据均为说明方法的假设，不是压测结果。涉及退款、补发或对外承诺的动作，必须遵守企业实际权限与审批制度。

本版包含 Evidence-Gated-Memory（EGM）的修复前评估与后续源码升级：0.6 已实现嵌入式应用层、共享 PostgreSQL 后端和可选 HTTP；Aftercare 已有可执行的受限证据适配层，但完整业务运行时未完成，也没有生产验收。当前边界见 [ADR-0002](decisions/0002-embedded-egm.md)与[嵌入式接入](integrations/egm-embedded.md)，历史反例见[验证记录](research/evidence-gated-memory.md)。

如果要直接看“下一步怎么建”，请先读[工程总设计与 Mermaid 架构图](system-design.md)：它把部署、Session/Run、持久等待、事件、沙箱、EGM 和模型接口落到模块与验收边界。本篇保留背景、原理与研究过程。

很多 Agent Demo 的核心只有几十行：读取用户消息，调用模型，执行工具，把结果交给模型，再循环一次。

这个循环并没有错。问题在于，当它接入真实企业业务之后，一次任务可能持续三天，中间有两次人工审批、一次供应商超时、三封重复投递的邮件，以及一台恰好在操作成功后崩溃的服务器。

此时，真正困难的已经不是“模型下一步会调用哪个工具”，而是：

**谁有权继续这张工单？哪些动作已经发生？服务重启后从哪里继续？一千张工单同时进来时，应该让谁占用哪一种资源？**

本文用一个完整的跨境电商售后场景，解释这些问题为什么会把一个 Agent Demo 推向分布式系统设计，以及沙箱、Harness、消息系统、记忆和模型 API 分别应该站在哪里。

## 1. 先把业务说清楚：我们不是在做一个通用聊天机器人

假设我们服务多家跨境商家。消费者通过邮件或售后入口反馈：“订单一直没有收到，但物流页面显示已签收。”

一张工单可能经过这样的过程：

1. 识别订单、买家、店铺和问题类型，确认当前操作属于哪个租户。
2. 查询订单系统、承运商轨迹、历史联系记录和适用的售后政策。
3. 阅读买家提供的截图、签收证明或其他附件，发现地址、时间和签收信息之间的矛盾。
4. 缺少证据时，提出补充资料请求；需要联系承运商时，准备对应材料。
5. 形成处理建议：继续等待、补充调查、安排退换货，或者提交需要审批的补发与退款方案。
6. 等待买家、商家或承运商反馈，数小时甚至数天之后继续。
7. 完成经过授权的动作，把结果同步到业务系统，保留可核验的记录。

“索赔”只是其中的一条支线。文章讨论的是售后工单处理，不是专门自动申请赔偿的机器人，也不把退款权限默认交给模型。

这类流程并非为了容纳技术名词而虚构。以 UPS 的公开理赔流程为例，实际处理会涉及运单信息、价值证明、补充材料和进度查询。这里借它说明业务天然存在“证据收集—等待—继续”的结构，不把某一地区的承运商规则泛化为所有国家和平台的售后规则。[UPS 理赔流程](https://www.ups.com/us/en/support/file-a-claim)、[材料要求](https://www.ups.com/us/en/support/file-a-claim/supporting-documents)

Agent 的价值主要在处理不整齐的信息：理解不同语言的描述，关联多个系统，解释相互冲突的证据，为人工提出有依据的建议。

金额计算、订单归属校验、退款权限、重复操作检查等部分，仍应尽量由确定性的业务代码负责。让模型参与业务，不等于让模型决定所有业务规则。

## 2. Demo 与企业级系统，差的不是多开几个进程

Demo 往往把几个原本不同的生命周期重叠在一起：

~~~text
一次 HTTP 请求
  = 一段 Agent 循环
  = 一份进程内状态
  = 一个临时工作目录
  = 一次用户可见任务
~~~

只要请求还没断、进程还活着、工具没出异常，这种写法就能很好地演示能力。

企业系统则必须把它们分开。

| 问题 | Demo 中常见做法 | 本文的企业级设计 |
|---|---|---|
| 接到任务 | 直接在请求里执行 | 先持久化受理结果，再安排执行 |
| 任务状态 | Python 对象、聊天记录 | 可版本化的工单、Run 和检查点 |
| 多人使用 | 多开协程 | 租户配额、任务调度、分资源限流 |
| 工具执行 | 模型要求什么就调用什么 | 身份、参数、策略、审批和幂等检查 |
| 失败重试 | 整段循环再跑一次 | 区分未执行、已成功和结果未知 |
| 等待人工 | 进程里等待 | 持久化等待条件，释放活跃执行资源 |
| 临时环境 | 长期共用目录 | 按信任边界分配隔离环境 |
| 用户断线 | 任务可能中断 | 界面订阅与后台任务生命周期解耦 |
| 调试与审计 | 看日志 | 性能追踪与业务审计分别建设 |

这里的“企业级”不是特定技术栈认证，也不意味着必须先装 Kubernetes、Kafka 和十几种中间件。

它更接近一组可验证的性质：接受的任务不会悄悄消失，错误不会静默变成成功，租户不会相互越权，昂贵资源有上限，关键动作能够核对，发生故障时有明确的恢复路径。

## 3. 先统一对象：工单、Agent、Worker 和沙箱不是同一个东西

讨论并发之前，需要给几个对象起准确的名字。

| 对象 | 含义 | 在本案例中的例子 |
|---|---|---|
| Case，业务工单 | 对业务人员有意义的长期对象 | 某订单的“未收到货”售后单 |
| Run，一次运行 | 在某份输入与版本下推进工单的一次执行 | 新证据到达后重新分析 |
| Step，执行步骤 | 可识别、可记录的工作单元 | 查询轨迹、分析附件、提交审批 |
| Attempt，尝试 | 某步骤的一次执行尝试 | 查询物流第一次超时后重试 |
| Worker，执行进程 | 承接执行任务的服务实例 | 一个运行 Harness 的进程 |
| Session，交互会话 | UI 或模型交互使用的上下文标识 | 客服打开工单后的交互会话 |
| Sandbox，沙箱 | 某些工具执行所需的隔离环境 | 运行附件解析脚本的临时环境 |

一张 Case 可以有多个 Run，一个 Run 可以有很多 Step，一个 Step 可以有多个 Attempt。

一个 Worker 可以同时承载多个等待 I/O 的运行，也可以只承载少量计算密集型步骤。一个 Run 可以完全不需要沙箱，也可以分阶段使用多个沙箱。多个子 Agent 也可能在同一个受控工作区内协作。

因此，不能从“有 1,000 个 Agent 任务”直接推出“需要 1,000 台虚拟机”。

更实用的说法是：**任务是逻辑对象，Worker 是执行者，沙箱是可分配资源。它们之间的映射应由资源需求与信任边界决定。**

## 4. 并发从哪里来？先看等待，而不是先看线程数

售后业务天然存在多种并发来源：

不同商家的工单同时到达；同一商家的营销活动产生峰值；历史工单在物流状态改变后同时恢复；同一工单可以并行查询订单与物流；一个任务又可能依次经历模型调用、浏览器操作和等待人工。

这些并发不是同一个指标。

我们至少应该区分：

- 已受理但尚未结束的工单数量。
- 当前可以被调度的运行数量。
- 正在占用 Worker 执行槽的运行数量。
- 正在进行的模型请求数量。
- 正在使用的浏览器或代码沙箱数量。
- 对某个业务系统正在发出的请求数量。

### 4.1 一个带单位的容量示例

假设系统平均每秒受理 2 张工单，每张工单从受理到关闭平均持续 6 小时。

在近似稳定的系统中，Little 定律给出：

~~~text
平均在途工单数 = 到达率 × 平均停留时间
              = 2 张/秒 × 21,600 秒
              = 43,200 张
~~~

这不意味着要为 43,200 张工单维持 43,200 个进程或沙箱。大部分工单可能在等待外部反馈。

再假设每张工单在整个生命周期内，累计占用逻辑执行槽 30 秒、发起 4 次模型请求、每次平均占用模型连接 3 秒，其中 25% 的工单会使用 20 秒沙箱。这些也是示意值。

在同样的稳态假设下：

~~~text
平均执行槽需求   ≈ 2 × 30       = 60 个
平均模型并发需求 ≈ 2 × 4 × 3    = 24 个
平均沙箱占用需求 ≈ 2 × 25% × 20 = 10 个
~~~

三个数字都不是最终配置。峰值、长尾、失败重试、资源碎片和期望排队时间都会改变实际容量。

这个例子的意义是说明：四万多张在途工单，与几十个活跃执行槽、十几个沙箱，可以同时成立。

### 4.2 吞吐瓶颈必须换算到同一种单位

如果模型账户有 RPM 和 TPM 限额，不能直接计算：

~~~text
min(RPM, TPM, 沙箱数量)
~~~

这些量的单位不同。

若每张工单平均需要 m 次模型调用、消耗 t 个供应商限额计数口径下的 Token，沙箱使用概率为 p，平均占用时间为 s 秒，沙箱容量为 C，则可以先换算成“工单/秒”：

~~~text
请求数约束下的工单吞吐 ≈ RPM / (60 × m)
Token 约束下的工单吞吐 ≈ TPM / (60 × t)
沙箱约束下的工单吞吐 ≈ C / (p × s)
~~~

这仍只是估算上界。供应商可能分别限制输入和输出 Token，不同模型有独立配额；实际请求有突发性，并非均匀分布。生产配置必须结合真实请求分布和限额规则测量。

更重要的是，每一步只申请自己即将使用的资源。不要让任务提前占住沙箱，再花几分钟排队等待模型额度。

## 5. 参考架构：业务状态在服务端，沙箱按需分配

本文选择的起点是：

**Harness in Service；PostgreSQL 作为业务状态与任务持久化的起点；EGM 作为证据准入的优先验证对象；高风险工具按需进入沙箱；模型调用通过薄适配层接入。**

这不是“所有业务都应该这样做”，而是因为本案例中，业务审批、工单状态、租户权限和外部系统回执比持续驻留的一整台个人电脑更重要。

~~~text
买家消息 / 客服界面 / 物流 Webhook
                  │
                  ▼
         接入服务：认证、验签、去重
                  │
                  ▼
     PostgreSQL：Case / Run / Checkpoint
                 Event / Action / Outbox
                  │
          调度器 / 持久定时器
                  │
                  ▼
          Worker + 业务 Harness
           │         │         │
           │         │         └── Evidence Adapter → EGM / 受控记忆
           │         └──────────── 模型网关 → 模型 API
           ▼
     工具与权限网关
           ├── 受控业务 API：订单、物流、工单系统
           └── Sandbox Manager → 浏览器 / 脚本 / 附件处理

证据与产物 ──→ 对象存储
运行指标与追踪 ──→ OpenTelemetry 管线
业务进度事件 ──→ 前端事件投影 / 可选 ACP 适配器
~~~

图中的网关、调度器和管理器首先是逻辑模块，不要求一开始拆成独立微服务。初版可以放在同一套代码库中，以 API 进程和 Worker 进程分别部署。

PostgreSQL 是运行状态的权威存储；订单和退款等领域数据仍以对应业务系统为准。对象存储保存附件、截图和报告；日志与追踪用于诊断。不要把这些职责全部压进聊天记录。

EGM 的证据与任务解释图位于控制服务侧，不要求跟着临时沙箱一起销毁。工具网关先认证来源、核对订单与回执含义，再导入证据。EGM 返回可用事实或补证据建议，但不授予动作权限，也不接管 Case / Run 的最终状态。

### 5.1 最小但有边界的数据模型

这里不展开完整生产 Schema，只展示必须能够表达的关系：

~~~text
case
  tenant_id, case_id, order_id, status, version

run
  tenant_id, run_id, case_id, state, checkpoint_ref
  lease_owner, lease_expires_at, fencing_token, next_wakeup_at

step_attempt
  run_id, step_id, attempt_id, status, input_hash, result_ref

action
  tenant_id, action_id, case_id, operation_type
  payload_hash, approval_ref, idempotency_key, provider_receipt, state

event
  event_id, tenant_id, aggregate_id, aggregate_version
  event_type, schema_version, occurred_at, payload_ref

outbox
  outbox_id, event_id, destination, available_at, delivery_state
~~~

这些字段各自解决具体问题。租约标识当前执行权；fencing token 排除旧持有者；action 追踪不可随意重做的业务操作；event 记录语义变化；outbox 解决事务提交之后如何可靠通知其他组件。

不必把每张表都做成“纯事件溯源”。数据库中保留当前状态，同时事务性写入关键业务事件，是一个更容易落地的起点。

## 6. Harness 到底做什么：它是运行控制器，不只是 Prompt 模板

模型本身只负责根据输入产生输出。它不知道你的数据库事务何时提交，也不能独立证明某笔退款已经到账。

Harness 是包围模型调用的执行控制层。它负责组装上下文、调用模型、解读工具请求、检查权限、调度工具、保存结果、决定继续还是暂停，并把运行状态交给持久化层。

对于售后 Agent，我会把 Harness 分成三部分：

第一部分是模型交互循环，负责供应商协议、消息历史、工具调用关联和流式输出。

第二部分是业务执行规则，负责订单归属、流程状态、证据要求、审批、预算和允许的工具集合。

第三部分是运行基础设施，负责检查点、租约、取消、重试、超时和事件记录。

这三部分不宜写成一个巨大 while 循环。否则更换模型协议，可能会意外影响退款审批；增加重试，可能会重复发送邮件。

### 6.1 外层是持久状态机，内层可以是动态 Agent

售后工作不适合把所有步骤提前固定成一个静态 DAG，但也不应该允许模型无限自由地操作。

一种实用的折中是：

~~~text
外层业务状态：
受理 → 调查 → 等待补充 / 等待审批 → 执行获批动作 → 跟踪 → 关闭

调查阶段内部：
模型可以选择查询哪些获准数据、比较哪些证据、
是否提出进一步调查，但受工具权限、预算和退出条件约束。
~~~

依赖关系明确的读取可以并行，例如同时查询订单与物流。需要先获得订单号才能查询的操作必须保持依赖。退款与“确认不退款”之类互斥动作，则不能因为模型同时提出了两项工具调用，就并行执行。

多个子 Agent 也不等于多个独立老板。它们应该共享父任务的预算和权限上限；涉及同一业务对象的写入，需要通过统一的操作入口和版本校验。

### 6.2 一次执行片段的逻辑

下面是职责顺序，不是可以直接复制到生产的实现：

~~~text
取得 Run 的执行权，读取最新检查点
→ 检查取消、预算、权限与当前业务版本
→ 核对所需证据版本与时效，组装本轮协议上下文和证据上下文
→ 请求模型，保存有效输出和协议关联信息
→ 对工具意图做 Schema 校验与策略判断
→ 普通读取：受限并行执行
→ 高风险动作：登记 Action，进入审批或受控提交
→ 保存工具原始结果、检查点和必要的业务事件
→ 将已核验的证据交给 Evidence Adapter，准入结论并更新解释投影
→ 继续下一步，或持久化等待条件后结束本次执行片段
~~~

工具参数“符合 JSON Schema”只是最外层条件。

例如模型产生 order_id，系统还必须确认这张订单属于当前租户；模型产生金额，系统还必须按权威订单数据和政策计算上限；模型引用“经理已经批准”，系统必须查到真正的审批记录。

自然语言、文档中的指令和记忆中的描述，都不能直接变成业务授权。

采用 EGM 也不改变这条规则：模型只提出候选结论和补查意图；source_system、TTL、观察时间、节点类型和业务对象绑定由受信任代码控制。EGM 的 suggested_action 仍要经过正常工具权限与审批，不能因为“缺少退款回执”就自动执行一次退款来补证据。

## 7. Harness in Sandbox 与 Harness in Service：分的是位置，不是能力等级

两种部署方式的核心区别是：**控制模型循环的那段程序放在哪里？**

### 7.1 Harness in Sandbox

整个 Agent 运行程序放进隔离环境中。它在里面调用模型、读写工作区、启动浏览器或执行命令；外部平台负责创建环境、传入任务、接收事件和管理生命周期。

这种方式适合复用一个成熟的完整 Agent 程序，尤其当它强依赖本地文件系统、终端、浏览器和持续工作区时。

但外部平台仍需考虑：任务是否已受理，沙箱失联后谁恢复，审批记录在哪里，调用了哪些外部动作。把 Harness 放进虚拟机不会自动得到持久工作流。

### 7.2 Harness in Service

Agent 循环在应用服务或 Worker 中运行。需要浏览器、代码执行或附件处理时，才把具体操作交给沙箱。

对本文的售后 Agent，这更容易把业务状态、策略与审批集中管理，也可以让大量等待中的工单不占用整套执行环境。

不过，“在 Service 中”也不自动等于可恢复。若状态仍只存在内存里，服务重启一样会丢失上下文。

| 维度 | Harness in Sandbox | Harness in Service |
|---|---|---|
| 循环位置 | 隔离环境内 | 应用服务或 Worker |
| 工具体验 | 本地环境集成自然 | 需要明确的远程工具接口 |
| 复用现成完整 Agent | 通常更直接 | 往往要做接口适配 |
| 沙箱损坏影响 | 可能同时丢失未外置的循环状态 | 控制状态可独立于工具环境保存 |
| 策略与审计 | 需要可靠向外报告和受控出口 | 更容易集中，但仍须实现 |
| 本文取舍 | 作为特定执行器的备选 | 主方案 |

两者完全可以混合：平台用持久工作流管理工单，其中一个调查步骤委托给沙箱里的完整 Agent。关键是声明清楚子任务的输入、产物、权限、预算和失败语义，不能让内外两套循环争夺同一张工单的最终状态。

## 8. 沙箱到底保护什么？为什么不能直接把所有工具放进业务服务器？

本文的沙箱，是为具有较高风险或特殊环境需求的工具提供的隔离执行环境。

查询自己实现的订单 API，通常不需要新建一台虚拟机。执行模型生成的 Python、处理来源不明的附件、打开外部网页并运行浏览器，则更值得放进明确受限的环境。

原因并不只是“模型可能写错代码”。附件解析器可能有漏洞；网页内容可能诱导 Agent 外传数据；脚本可能消耗大量 CPU、内存或磁盘；长期浏览器可能保留错误租户的 Cookie。

沙箱降低的是这些行为对宿主、其他任务和其他租户的影响范围。它并不能保证模型判断正确，也不能自动阻止一个拥有合法退款凭证的程序误用退款 API。

### 8.1 E2B 与 Kubernetes 不是同一层的二选一

E2B 提供围绕沙箱创建和使用的开发接口与基础设施，其公开基础设施使用 Firecracker microVM。使用托管服务，是把相当一部分底层环境生命周期工作交给供应商；阅读或部署开源基础设施，则意味着自行承担对应的运维工作。开源与“自托管和托管服务具有相同运维成本、能力及 SLA”是两回事。[E2B 基础设施仓库](https://github.com/e2b-dev/infra)

Kubernetes 是工作负载编排平台，本身不是“Agent 业务调度系统”。普通 Pod 也不天然具有 microVM 级别的隔离。

Kubernetes SIGs 的 Agent Sandbox 项目在 Kubernetes 上提供沙箱生命周期相关抽象，包含 Sandbox、模板、申请和预热池等能力。实际隔离强度仍取决于集群配置和所用运行时，例如是否配置 gVisor 或 Kata，而不是由资源对象名称中的 Sandbox 一词保证。[Kubernetes Agent Sandbox](https://github.com/kubernetes-sigs/agent-sandbox)

| 层次 | 主要问题 | 典型选择 |
|---|---|---|
| 业务控制层 | 哪张工单可运行、预算多少、何时审批 | 应用状态机与调度器 |
| 沙箱控制层 | 创建、申请、回收、预热哪些环境 | E2B 接口或 Agent Sandbox 等 |
| 工作负载编排层 | 进程或 Pod 放在哪台机器、资源是否足够 | Kubernetes 等 |
| 隔离运行时层 | 执行代码与宿主之间的安全边界 | 容器、gVisor、Kata、Firecracker 等 |

这张表是职责分类，不表示所有项目都按同一方式组合，也不表示 E2B 必须运行在 Kubernetes 上。

### 8.2 本项目如何选

如果目标是尽快验证售后业务效果，团队没有虚拟化或集群运维能力，而且数据与网络要求允许使用外部沙箱，我会先试 E2B 托管，并把调用封装在自有 Sandbox Adapter 后面。

如果企业已经有成熟 Kubernetes 平台，并且要求运行在自己的网络与数据边界内，可以评估 Kubernetes Agent Sandbox，明确运行时、出网控制、容量扩展和升级责任。

如果希望采用 E2B 的开源基础设施自托管，也应独立评估部署环境、虚拟化能力、镜像构建、快照存储、监控和故障处理，不因为“仓库可下载”就把它当作普通无状态 Web 服务。

核查时，公开仓库列出的自托支持包括 GCP 和 AWS Beta，自托指南涉及多项云资源与基础设施组件。这不等于任意 Linux VPS 都可以一键安装；商业交付范围也不能直接套用到开源部署脚本上。[E2B 自托指南](https://github.com/e2b-dev/infra/blob/main/self-host.md)

这里不存在一个脱离企业现状的全局最优选项。本文默认通过统一接口按需申请沙箱；具体后端由合规边界与平台能力决定。

### 8.3 隔离粒度：按信任边界分配，不按 Agent 名字机械分配

售后业务中的一个合理起点是：同一工单的高风险调查步骤，可以使用同一临时工作区；不同租户默认不共享带有数据或凭证的工作区。

如果一个订单涉及多个工单，是否共用环境还要看并发写入和权限范围，不能只按 order_id 做复用。

对于可信的内部 API 工具，并发通常在服务侧控制；对于执行不可信代码的工具，环境边界应更严格。不要为了省启动时间，把不同商家的登录 Cookie、订单附件和模型脚本都留在一个长期共享目录里。

推荐的控制包括：

- 非特权运行，不挂载宿主敏感目录或容器管理 Socket。
- 限制 CPU、内存、磁盘、进程数、执行时间与产物大小。
- 默认收紧出网，阻止访问云元数据和不需要的内部服务。
- 将凭证限制到租户、工具、资源范围和短期有效期。
- 对附件、网页与工具输出维持“不可信输入”的标记。
- 在环境回收前保存需要保留的产物，在再次分配前证明环境干净。

高权限业务密钥尤其不应直接交给任意代码执行环境。更好的办法是让沙箱调用受控工具网关，由网关再次校验动作和权限，或者只接收已经裁剪过的输入数据。

## 9. 任务如何跨越进程重启：检查点、等待条件和恢复

工单可能存活三天，Worker 不必活三天。

这要求系统保存的不只是“聊到了哪一句”，还包括运行当前处于哪个阶段、正在等待什么、哪些工具已完成、哪些动作尚未确认，以及下一次运行需要哪些版本的数据。

### 9.1 检查点不是聊天记录的别名

一个可恢复检查点至少应该能定位：

~~~text
业务阶段与工单版本
当前计划及未完成步骤
模型协议所需的消息或输出项
工具调用 ID 与持久化结果
正在等待的事件、审批或定时器
已登记业务操作的 action_id
剩余预算、运行策略版本、产物引用
~~~

模型上下文可以压缩，业务操作记录不能因为聊天摘要删除而消失。

恢复也不一定是“从某一行代码继续”。在多数应用中，它更像：读取状态，确定下一项尚未完成且允许执行的工作，再进入一个新的执行片段。

### 9.2 长等待与短等待要分开

等待买家上传材料时，系统应该保存等待条件，释放 Worker 的活跃执行槽和不再需要的沙箱。新消息到达，或持久定时器到期后，再安排任务恢复。

不能简单依赖一个进程里的 sleep(86400)。进程重启后，这个定时器可能就没有了。

等待模型 API 返回则有所不同。使用异步 I/O 可以让线程处理其他工作，但这个请求仍然占用模型并发额度，并且通常仍由当前 Worker 持有逻辑执行权。

只有供应商提供可重新查询的异步任务标识，且应用已经持久化该标识与恢复逻辑时，才可以把“等待这次远程计算”设计成跨进程恢复的等待。

**释放 CPU、释放 Worker 执行槽、释放模型请求额度和释放沙箱，是四件不同的事。**

### 9.3 外部事件与定时器可能同时到达

买家回复与超时提醒可能在同一瞬间触发；Webhook 也可能被重复投递。

恢复入口需要先做来源校验与事件去重，再用工单版本或等待条件版本判断事件是否仍然有效。

还存在一个更隐蔽的竞态：外部回复可能先于等待条件提交到达。合法外部事件应该先写入持久 Inbox，不能只因当时没有匹配的等待条件就丢弃。登记或恢复等待时，应核对已到达但尚未匹配的事件，并通过同一业务对象的版本控制或可重试匹配机制收敛，避免永久漏唤醒。

例如等待条件 W7 已被“收到买家回复”满足，稍后到达的 W7 超时事件不应该把工单重新推进到“买家未回复”的分支。

同一业务对象可以存在多个 Run，但需要明确哪些状态转换必须串行，哪些更新允许通过乐观并发控制合并。只给每个 Run 加锁，不能解决两个不同 Run 同时修改同一订单的问题。

## 10. 租约与心跳：如何决定谁现在有资格执行

当系统只有一个 Worker 时，“这张任务归谁”看起来没有问题。一旦多副本运行，或者机器暂时失联后恢复，这个问题就会变得具体。

### 10.1 为什么使用租约，而不是永远持有一把锁

租约是一种有到期时间的执行权。Worker 成功领取任务后，获得有效期限与一个递增的 fencing token，并定期续租。

领取过程必须是原子的。例如在 PostgreSQL 中，可以在短事务内选出可执行任务、锁住对应行并写入租约；其他 Worker 跳过已锁定的行。事务结束后再执行网络请求，不能拿着数据库行锁等待模型几分钟。

运行中的关键写入也应带上持有者标识与 fencing token，并在同一条条件更新中检查有效性。租约判断尽量使用数据库侧的时间基准，避免直接信任不同 Worker 的本地时钟。

心跳只是租约续期的一种机制，不是“Agent 每隔一会儿再问一次模型”。

### 10.2 心跳、进度与超时分别解决不同问题

| 机制 | 回答的问题 |
|---|---|
| 存活检查 | 进程是否还能响应？ |
| 租约心跳 | 这个执行者是否还保持当前任务的执行权？ |
| 进度记录 | 业务步骤是否真的在推进？ |
| 步骤超时 | 某项工具或模型请求是否已经等太久？ |
| 运行预算 | 整个 Run 是否超过时间、成本或步骤限制？ |
| 业务定时器 | 明天是否需要追问承运商或提醒客服？ |

后台线程一直发送心跳，不代表主执行循环没有卡死。因此还需要“多久没有完成有效步骤”的检测，以及具体工具的超时机制。

租约时长和心跳间隔也不是某组神奇默认值。可以用“30 秒租约、10 秒续租”解释机制，但配置前仍要测量调度延迟、网络抖动、暂停时间和期望故障接管速度。

### 10.3 仅有租约，还会出现旧 Worker 继续执行

考虑下面的时间线：

~~~text
t0  Worker A 取得任务，token = 41
t1  A 长时间暂停或与控制数据库失联
t2  租约到期，Worker B 取得任务，token = 42
t3  A 恢复，仍然以为自己应继续工作
~~~

如果 A 的状态写入不带版本条件，就可能覆盖 B 的进度。fencing token 的作用，是让受保护的资源拒绝旧持有者的写入。

但是，**只在数据库里检查 token，不能阻止 A 绕过数据库直接调用外部退款 API。**

受控工具网关也需要检查当前执行权与操作记录。即使检查时有效，从检查到外部请求真正发出之间仍然可能发生执行权变化，这是一种检查与使用之间的竞态。

可以在短事务中把租约校验与 Action 的本地受理登记绑定，约束谁能提交到本地执行机制；但这个事务不能覆盖任意外部 HTTP API。已经发出去的请求也不能仅靠租约到期撤回。这正是为什么还需要目的端幂等和结果核对。[etcd 关于租约与外部资源互斥的说明](https://etcd.io/docs/v3.6/learning/why/)

分布式锁不是通往“绝对不会重复执行”的捷径。它管理的是执行权，不是所有外部系统的实际状态。

## 11. 最难的一种失败：工具成功了，但系统没来得及记下来

设想一个已经经过人工批准的补发动作：

1. Worker 写入“准备提交补发”的操作记录。
2. 订单系统接受了补发请求。
3. Worker 在保存回执之前崩溃。
4. 新 Worker 读取到一个没有成功回执的操作。

这时，直接重试可能导致第二张补发单；直接标记失败又可能误导客服。

所以，至少需要区分三种结果：

**明确没有发生、明确已经成功、可能发生但目前未知。**

结果未知不是普通失败，应该成为显式状态。

### 11.1 为外部副作用建立 Action Ledger

可以使用如下操作状态：

~~~text
PROPOSED → APPROVED → DISPATCHING → CONFIRMED
                           │
                           └── UNKNOWN → 查询 / 对账 / 人工确认
~~~

部分普通动作不需要人工审批，但仍需要策略授权。这里的 APPROVED 可以表示已完成所需授权，不意味着每封普通通知都必须人工点击。

操作记录要在请求发出前持久化。Worker 恢复时，发现停留在 DISPATCHING 且无可靠结果的动作，应按“可能已发生”处理，而不是假设从未发送。

幂等键对应的是一个稳定的业务操作，不能在每次网络重试时重新生成。多个 Run 如果试图发起同一业务效果，也应通过业务唯一约束或统一操作登记机制归并，而不只是依赖单个 Run 内去重。

如果外部平台支持可靠的幂等键与结果查询，可以用同一业务操作标识重新查询或按其契约重试。还要考虑平台幂等记录的有效期限。

如果平台不支持幂等，也没有可靠查询方式，就必须接受系统无法仅靠本地事务证明“只发生一次”。高风险情况下，应进入核对或人工处理，而不是无限自动重试。

### 11.2 审批必须绑定具体动作

“这张工单允许退款”过于模糊。审批记录至少应绑定：

~~~text
租户、订单、操作类型、金额与币种
收款或目标对象、请求内容摘要
审批人、审批时间、有效期、适用策略版本
~~~

审批后如果金额、目标对象或其他关键参数变化，原审批不能自动覆盖新动作。

工具权限弹窗、模型输出“已获得许可”、聊天里的一句同意，都不应该绕过企业所需的身份校验和审批记录。

### 11.3 重放时不要把副作用重做一遍

恢复运行时，已经成功的工具结果应该通过持久化记录回填。

即使模型重新生成了一段不同的计划，系统仍需要识别其中是否包含已经完成的业务操作。不能把“重新跑模型”当作“安全地重新跑整张工单”。

这里也没有必要承诺 Token 级确定性重放。更合理的目标是：业务事实可核对，关键决策输入可追溯，已经发生的副作用不会因恢复过程被盲目重做。

EGM 可帮助发现“缺少声明要求的回执”，但“存在 refund_api_response”本身不证明请求成功。连接器必须核验回执状态、租户、订单、金额、币种及 action_id；未知结果仍留在 Action Ledger 的核对流程中。EGM 的 Fact accepted、TaskNode DONE 与外部动作 CONFIRMED 不能合并成一个布尔值。

## 12. 持久消息系统：它负责可靠传递，不负责理解售后业务

消息队列的作用，是在组件之间缓冲、传递和分配工作，并根据具体机制支持重投、回放和消费确认。

它不知道“给买家发送了一封邮件”是否等价于“这张售后工单成功结束”。它更不知道退款请求是否真正产生了一笔交易。

### 12.1 先解决数据库与消息之间的双写

一种危险写法是：

~~~text
先把工单状态写入数据库
再向消息系统发送“继续处理”通知
~~~

两步之间崩溃，工单可能已经受理却无人执行。反过来先发消息，再提交数据库，也有消费者看到不存在或尚未提交状态的问题。

本文采用事务性 Outbox：

~~~text
同一个数据库事务：
  更新业务状态
  写入关键业务事件
  写入待投递 Outbox

事务提交之后：
  投递器读取 Outbox
  发送通知
  记录投递结果
~~~

投递器仍可能在“消息发送成功、记录投递成功之前”崩溃，因此可能重复发送。消费者要用持久 Inbox、事件唯一键或等价机制去重。

如果消费效果是在同一个数据库中推进状态，Inbox 去重记录与对应状态变化或持久任务移交，应在同一事务中提交。不能先标记“已消费”，再另行更新业务：中间崩溃后，重投会被跳过，业务却从未推进。外部副作用不能靠这个本地事务包住，仍按 Action Ledger 的规则处理。

消费确认应该发生在本阶段结果已可靠保存之后，或者任务已经被可靠移交给下一段持久执行机制之后。仅仅“把任务放进内存”不构成可靠移交。

这解决的是可恢复传递，不是依靠一张表就得到端到端恰好一次。

### 12.2 为什么本文先用 PostgreSQL

如果业务数据库已经是 PostgreSQL，任务量尚未证明需要独立 Broker，那么任务表、事件表、Outbox 和定时器表可以组成一个相对简单的起点。

多个 Worker 用短事务领取任务，业务状态与待执行记录可以一起提交，运维组件少，也方便理解故障边界。

PostgreSQL 的 SKIP LOCKED 适合某些类似队列的多消费者访问模式，但它会跳过被锁定的行，并不保证全局公平或严格 FIFO。任务优先级、租户公平性和饥饿检测仍需要应用处理。[PostgreSQL SELECT 锁定子句](https://www.postgresql.org/docs/current/sql-select.html)

LISTEN/NOTIFY 可以用于唤醒正在轮询的 Worker，但不是持久消息日志。真正的待处理任务仍在表中；即使通知丢失、连接断开或服务重启，也应能通过扫描表恢复。[PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)

长期运行后还需要治理表增长、索引、归档、清理、连接池与数据库负载。不要把所有逐 Token 输出和大型附件塞进任务表，指望数据库无限承担队列、日志、文件系统和分析仓库的全部角色。

### 12.3 Kafka、NATS JetStream、Redis Streams 怎么选

| 方案 | 更值得考虑的条件 | 必须认清的边界 |
|---|---|---|
| PostgreSQL 任务 / 事件表 | 已有 PostgreSQL，希望业务与调度状态事务一致，规模和运维负担可控 | 需要自己处理领取、租约、重试、归档、公平性；不是现成工作流引擎 |
| Kafka | 有持续事件流、多个独立消费者、较强的回放需求，并已有相应运维能力 | 分区内顺序不是全局顺序；Kafka 事务不自动覆盖外部业务 API |
| NATS JetStream | 希望使用持久流、确认与重投，并结合 NATS 消息体系 | 要正确配置存储、复制、保留、消费者和确认；Core NATS 与 JetStream 的语义不同 |
| Redis Streams | 团队熟悉 Redis，需要消费组与待处理消息管理，负载与持久化配置适合 | 消费组不是全部可靠性；须处理 Pending、认领、裁剪、持久化和故障转移 |
| 其他持久队列 | 云托管队列或 RabbitMQ 等更符合现有平台 | 分别核实确认、可见性、保留、重投和故障模型，不按“消息队列”四字假定一致 |

Kafka 的事务与恰好一次处理有明确边界，写入外部系统仍需要目标系统协作。JetStream 的消息去重和确认机制，也不替业务代码完成退款幂等。Redis Streams 的具体能力会随版本变化，系统设计应固定实际使用的版本，而不是把所有版本概括成同一套特性。[Kafka 交付语义](https://kafka.apache.org/43/design/design/)、[JetStream 发布与去重](https://docs.nats.io/learn/jetstream/publishing)、[JetStream 交付与确认](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment)、[Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)

这里更重要的问题不是“哪个中间件更先进”，而是：是否真的需要多个下游独立消费历史事件，队列延迟是否已经成为瓶颈，团队是否具备该组件的运维能力。

如果已经采用 Temporal 一类持久工作流引擎，定时器、活动重试和历史恢复中的一部分职责可以交给它。应明确谁拥有工作流状态，不再平行自建一套争夺权威的调度状态机；外部副作用的幂等与核对依然需要业务处理。[Temporal 持久执行](https://docs.temporal.io/)

### 12.4 顺序与去重必须对准业务对象

通常没有必要让所有商家的所有事件全局有序。更实用的是按需要串行的 Case、订单或其他聚合对象确定顺序范围。

事件应携带稳定 event_id、业务对象标识、版本和 Schema 版本。消费者依据业务版本拒绝过时更新或触发补查，而不是假设 Broker 永远不会乱序、重投或发生并发处理。

同一个 event_id 的重投可以去重；同一张工单的两个不同物流更新不能仅因为 case_id 相同就丢掉其中一个。去重键的粒度必须与事件或操作语义一致。

## 13. ACP、业务事件、模型流和 OpenTelemetry，为什么不能混为一谈

它们都可能表现为“一条条事件”，但对象和承诺不同。

| 事件类别 | 表达什么 | 是否足以恢复业务 |
|---|---|---|
| 模型 API 流式事件 | 文本增量、工具参数增量、生成状态 | 不足以单独恢复完整业务 |
| ACP 交互消息 | 客户端与 Agent 之间的会话、工具进度与许可交互 | 会话能力不等于业务事务恢复 |
| 持久业务事件 | 工单受理、证据保存、审批完成、动作确认 | 是恢复输入之一，需配合状态和操作记录 |
| OpenTelemetry 信号 | 哪段执行耗时、调用关系、错误与资源表现 | 用于诊断，不是完整业务账本 |

### 13.1 ACP 在这里具体指什么

本文的 ACP 指 Agent Client Protocol，即客户端与 Agent 之间的互操作协议，不是另一个同样可能缩写为 ACP 的 Agent Communication Protocol，也不是消息队列。[ACP 官方介绍](https://agentclientprotocol.com/get-started/introduction)

以稳定 v1 为准，客户端通过 session/prompt 提交输入，Agent 通过 session/update 通知发送消息、计划与工具进度；工具许可使用 session/request_permission 请求与对应响应。一次用户交互可以包含多次模型与工具调用。[ACP Prompt Turn](https://agentclientprotocol.com/protocol/v1/prompt-turn)、[ACP Tool Calls](https://agentclientprotocol.com/protocol/v1/tool-calls)

例如客服在界面看到“正在读取签收证明”“正在查询物流”，可以由相应适配器把内部运行事件映射成 ACP 进度通知。

但如果你只是开发自己的售后 Web 平台，没有兼容 ACP 客户端的需求，完全可以先实现自有业务事件接口。ACP 不应该仅因为名字里有 Agent 就进入必选依赖清单。

还要留意版本：v1 的标准 stdio 方式与远程传输草案，不能混成“任意云端连接都已标准化”；官方 v2 当前有独立草案，字段与生命周期不可直接混用。[ACP v1 Transports](https://agentclientprotocol.com/protocol/v1/transports)、[ACP v2 Draft](https://agentclientprotocol.com/announcements/acp-v2-draft)

### 13.2 会话恢复不等于工单恢复

ACP 支持具备相应能力的 Agent 加载会话并回放历史，因此“ACP 完全不支持恢复”也不准确。[ACP Session Setup](https://agentclientprotocol.com/protocol/v1/session-setup)

真正的边界是：重放一段“工具已执行”的会话，不等于核验那个外部动作的最终状态。工单仍然需要自己的 action_id、审批记录、结果回执和恢复规则。

同理，前端点击“允许”可以成为授权流程的输入，但不能替代后端确认用户身份、权限范围、具体动作参数和有效期。

### 13.3 先有内部业务事件，再做客户端投影

一个简化的持久业务事件可以这样表达：

~~~json
{
  "event_id": "evt_...",
  "schema_version": 1,
  "tenant_id": "merchant_...",
  "case_id": "case_...",
  "run_id": "run_...",
  "step_id": "step_...",
  "action_id": "action_...",
  "event_type": "action.confirmed",
  "aggregate_version": 18,
  "occurred_at": "2026-09-06T08:00:00Z",
  "payload_ref": "artifacts/receipt_..."
}
~~~

字段按事件类型取舍，不要求每条事件都含 action_id。tenant_id 必须由受信任的服务上下文确定，不能因为模型输出了某个值就信任它。

前端可以用 SSE 或 WebSocket 订阅这些事件的安全投影，断线后按服务端定义的提交顺序游标补取。游标的排序保证需要专门实现，不能简单假定随机 UUID、时间戳或分配过但尚未提交的数据库序号天然代表可靠提交顺序。

逐 Token 展示通常可以是短期数据；关键阶段变化和操作结果需要持久化。大附件放对象存储，事件只放引用和必要摘要。

用户关闭页面不应自动取消后台工单。取消需要一个明确、授权且持久化的操作；已经发生的邮件发送或退款也不会因为取消而自动回滚。

### 13.4 OpenTelemetry 回答的是“为什么慢、在哪里失败”

对于每次活跃执行片段，可以创建一段 Trace，模型调用、工具调用与数据库访问各自形成 Span。

任务等待两天之后再恢复时，没有必要维持一个两天不关闭的活动 Span。可以为新的执行片段建立新的追踪，并利用关联标识和适当的 Span Links 表达因果关系。[OpenTelemetry Traces 与 Span Links](https://opentelemetry.io/docs/concepts/signals/traces/#span-links)

我们真正想看到的问题包括：

- 排队耗时高，还是模型响应慢？
- 某个承运商接口的错误率是否突然上升？
- 沙箱启动是慢在资源不足、镜像准备还是应用初始化？
- 哪个租户或业务分支消耗了异常多的模型预算？
- 重试是否正在放大原本的故障？

OTel 的普通采样与日志保留策略不等于完整业务审计。审批与回执应该保存到有独立权限和保留策略的持久业务记录中。[OpenTelemetry Sampling](https://opentelemetry.io/docs/concepts/sampling/)

还需要区分 OTel 基础设施与 GenAI 字段的成熟度。核查时，GenAI 语义约定已迁移到独立官方仓库，相关说明仍标记 Development；落地时应固定所采用的规范与 SDK 版本，不宣称全部 GenAI 字段已经稳定。[OTel 语义约定](https://opentelemetry.io/docs/specs/semconv/)、[GenAI 约定状态](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md)

客户邮件、地址、密钥与完整 Prompt 不宜默认进入通用遥测平台。case_id、run_id 等高基数字段可以用于追踪关联，但不要无节制地作为所有指标的标签。

审计应记录可访问的输入、证据、工具参数、策略版本、审批和结果，不以获得模型完整内部思维链为前提。

接入 EGM 后，可以关联 evidence_id、fact_id、Schema 版本和拒绝原因，观察补证据成功率、错误拒绝和投影延迟。EGM 自身的审计记录也是补充材料，不代替业务审批与外部回执的独立保留策略。

## 14. 怎样真正提高并发：调度、背压、限流与预热

加 Worker 只解决一种容量。如果瓶颈是模型 TPM，增加 100 个 Worker 可能只会制造更多 429、重试和排队。

### 14.1 分资源控制，而不是一个全局并发数字

本文建议至少建立以下资源门槛：

~~~text
租户层：活跃运行数、待处理量、成本预算、优先级
模型层：供应商 / 模型的并发、RPM、TPM 与预算
工具层：每个平台、账号或租户的 API 速率限制
沙箱层：可分配环境、CPU、内存、浏览器会话
业务对象层：同一工单 / 订单的关键写入互斥与版本
~~~

某个步骤可能同时需要多个门槛。例如浏览器工具既受沙箱容量限制，又受网站或账号访问频率限制。

申请应有有界等待和一致的规则，避免 A 占着沙箱等模型、B 占着另一类资源等沙箱的循环等待。能提前做的无副作用准备可以提前做，昂贵资源则尽量临近使用时申请。

单进程 Semaphore 只限制当前进程。扩成十个副本后，若每个副本仍以为自己拥有全部额度，总量会被放大十倍。跨实例配额需要共享权威、集中准入，或受控分配给实例的额度片段，并定义额度持有者故障后的回收规则。

模型 Token 限流往往需要请求前估算、结束后按实际使用量结算。估算不足可能触发供应商限流，估算过大则降低利用率；不能把成本账单与所有供应商的限额计数规则简单等同。

### 14.2 公平性与背压同样重要

一个大商家的批量导入，不应永久饿死其他商家的少量紧急工单。

可以使用租户分层队列、加权公平分配和带上限的紧急优先级。具体权重应由服务等级与容量测试决定，不需要把一串手工评分包装成智能路由。

当积压超出可接受范围时，系统应明确展示排队、限制新批量任务、降低非关键分析成本，或按接入契约拒绝继续受理。已经返回“受理成功”的任务必须有可靠记录，不能为了保护 Worker 而静默丢弃。

重试也需要预算与退避抖动。收到供应商限流后立刻由所有 Worker 同时重试，可能形成比原流量更大的冲击。

### 14.3 预热解决冷启动，不创造物理资源

预热可以发生在不同层次：

| 预热方式 | 减少什么等待 | 成本与风险 |
|---|---|---|
| 提前构建模板或镜像 | 安装依赖、构建运行环境 | 镜像更新、安全扫描、存储成本 |
| 节点预拉取与缓存 | 镜像拉取与部分初始化 | 节点磁盘占用、缓存失效 |
| 预创建空闲沙箱 | 实例创建与启动 | 空闲资源成本、补池速率 |
| 预启动浏览器或工作进程 | 应用冷启动 | 内存占用、状态清理、版本一致性 |

Kubernetes Agent Sandbox 的 SandboxWarmPool 就是沙箱供给侧的预热机制，Claim 可以认领准备好的环境，控制器再补足空闲池。它维护的是待分配供给，不是售后业务的总并发上限。[Agent Sandbox Quickstart](https://agent-sandbox.sigs.k8s.io/docs/use-cases/examples/quickstart/)

例如机器最多支持 100 个符合资源要求的沙箱，保留 20 个空闲暖实例，并不会得到 120 个可用容量。认领后的实例、空闲实例和其他负载仍然共同消耗资源。

一波突发请求可能迅速耗尽暖池。如果补池速度赶不上需求增长，之后的请求仍会遇到冷启动。

### 14.4 如何估算暖池，而不是随手填一个数字

一个粗略起点是：

~~~text
希望保留的空闲供给
≈ 目标突发申请速率 × 补充可用环境所需时间
  + 为长尾与预测误差保留的余量
~~~

这只是局部估计，不包含所有回收、复用与资源竞争因素。应该采集暖池命中率、申请等待时间、补池时间、失败率和空闲成本，再调整目标。

伸缩也要分层：增加 Worker 副本、补充沙箱实例和增加底层节点是不同操作，控制循环的时延也不同。不能认为 Pod 数量变化就会即时增加物理机器。

暖池默认应该保存无租户凭证的干净模板。在认领时注入限定权限，不把上一个商家的 Cookie 或附件当成“缓存优化”交给下一个商家。

### 14.5 暂停与快照不等于业务回滚

环境快照可能保留进程、内存或文件状态，具体取决于实现。但它不会自动快照邮件服务器、支付系统、数据库和承运商平台。

恢复快照后，外部连接可能已经断开，短期凭证可能过期，页面登录可能失效，外部业务状态也可能改变。

因此，快照恢复后仍要重新校验权限和任务所有权，核对需要执行的动作。对于长时间等待的售后工单，保存持久检查点与必要产物，再重建执行环境，往往是值得优先考虑的策略。

## 15. 记忆与证据准入：先验证 EGM，再决定长期记忆平台

“Agent 有记忆”经常把几类不同数据混在一起。

| 数据层 | 例子 | 是否可以作为业务权威 |
|---|---|---|
| 业务事实 | 订单状态、退款记录、承运商回执 | 对应权威系统可作为依据 |
| 执行状态 | 待审批动作、已经执行的步骤、幂等键 | 决定流程如何恢复 |
| 证据准入与解释图 | EGM 中的 Evidence、Claim、Fact、TaskGraph | 检查证据条件，不能替代业务事实或执行权 |
| 长期记忆 | 买家偏好、审核过的处理经验、历史摘要 | 派生信息，可能过时或错误 |
| 本轮上下文 | 本次实际发送给模型的消息与检索结果 | 是模型输入，不代表全部事实 |

记忆系统的作用，是减少重复调查、维护有用的跨轮信息、按需找回经验。它不应该取代退款账本或执行检查点。

### 15.1 EGM 与本案例为什么匹配

Evidence-Gated-Memory 不只提供 add / search。它把原始证据、候选结论、门控、事实依赖与任务解释结构连接起来：结论需要声明支持证据，Schema 决定需要哪些证据类型及其时效，缺项时返回补查建议。

本次按固定提交 a16e3de7ca51727d6f16b8d335bb75ce70e9b4f6 核查了实现，而不是只读项目介绍。它已经有 record_evidence、assert_fact、transition_node、build_context、事实失效传播及候选记忆接口，适合成为当前案件“证据是否足够”的起点。[EGM 公共实现](https://github.com/yushui2022/Evidence-Gated-Memory/blob/a16e3de7ca51727d6f16b8d335bb75ce70e9b4f6/src/evidence_gated_memory/core/memory.py)

例如买家陈述、承运商签收记录和订单系统状态可以并存。系统不应把“买家报告未收到”升级成“承运商确认丢失”，也不应因为有一份 API 响应，就认为退款完成。

因此，本项目默认采用 **受控 Evidence Adapter + Worker 内嵌 EGM 应用层 + 共享 PostgreSQL**。代码包独立不意味着必须另起微服务；HTTP 是同一应用层的可选入口。Aftercare 的退款证据 Adapter 已实现，完整业务运行时仍待实现；EGM 始终不替代业务台账。

### 15.2 结构门控不是业务真值验证

以下是修复前 a16e3de 的行为。后续 0.5.0 已增加原始 JSON 字段契约，但仍不是任意自然语言的业务真值验证器。

本次运行了 65 个精选上游测试，全部通过；额外的合成探针却揭示了三个接入边界：

| 探针 | 修复前内置规则下的结果 | 必须保留的控制 |
|---|---|---|
| refund_api_response 的正文为 status=failed | “退款完成”的 Fact 与 DONE 都可通过 | 校验成功状态，失败响应不分类为成功证据 |
| 用 ORD-999 的响应支持 ORD-123 的结论 | Fact 与 DONE 都可通过 | 强制 tenant / case / order / action 绑定 |
| 同 workspace 中按 B 工单构建默认上下文 | 可能包含 A 的长期记忆 | workspace 隔离与检索权限；初期关闭长期记忆自动注入 |

这些是针对固定旧代码和 REFUND Schema 的历史观察。对应路径现已在 EGM 独立源码修复，Aftercare 业务接入仍未完成。[历史验证](research/evidence-gated-memory.md)、[新服务契约与测试](integrations/egm-service.md)

它们说明：EGM 的 Fact 是“通过当前规则的对象”，不是业务绝对真值。来源 allowlist 也只是标签匹配，真正的来源认证、对象绑定与字段校验必须由受信任连接器完成。

新 AFTERCARE Schema 可用 evidence_contracts 验证 JSON 成功状态及 tenant/case/order/action/amount/currency 绑定；仍需可信连接器认证响应、规范金额单位并从 Action Ledger 确定预期字段。不能只写一个证据类型名字就假定完成语义验证，任意模型叙述也不能因绑定字段通过而自动成为业务事实。

### 15.3 让 EGM 管解释投影，不让它成为第二个业务主系统

建议的数据流是：

~~~text
可信工具结果 → 原始证据持久化 → 业务字段校验
  → EGM 证据导入 → 候选结论准入 → 带引用的模型上下文

模型提出下一步 → Aftercare 权限、审批、版本与幂等检查
  → 执行或等待 → 回执核对 → 更新业务状态
~~~

PostgreSQL 中的 Case / Run / Action 保持权威。EGM TaskGraph 只解释调查进度，即使某个节点 DONE，也不能自动关闭工单或跳过审批。

撤销证据可以使依赖事实失效，但不会自动撤销节点完成状态，更不会回滚外部退款。Aftercare 应触发复核、重建相关判断；历史已确认动作继续保留在台账中。

模型 API 需要的工具调用 ID、工具结果与其他协议项也要保留。build_context 生成的是证据上下文，不是可以替换全部 Responses / Messages 历史的通用序列化格式。

### 15.4 EGM 的并发与持久化边界

0.6 将权限、schema 指纹、operation_id 幂等、expected_revision 和审计放在公共 EvidenceApplication，而不只放在 HTTP 层。SQLite 保留给本地使用；PostgreSQL 用 tenant/case 范围的对象行保存证据、图、原文和操作回执。每个操作在短事务内锁定当前工单，不同工单可以并发；当前同工单读取也会串行。模型、工具调用和等待不在数据库事务内。共享 PostgreSQL 不等于已经配置多节点高可用。

默认 EGM 调用自行提交，HTTP 也不会自动共享业务事务。若无法共享事务，应先持久保存来源事件与 Outbox，再可重试导入并维护对象映射和投影版本。嵌入式 PostgreSQL 接入可以显式 join 业务正在使用的同一个连接和外层事务，使业务写入与 EGM 投影一起提交；外层提交前不能 ACK 或发布成功。只有权威输入、策略与映射可靠保存并验证可重建，才可以把 EGM 数据当作可重建投影。这仍不使外部付款 API 成为本地事务的一部分。

回放保留原始观察时间，不以重建时间刷新 TTL。投影滞后时高风险决策等待或转人工。业务 Worker 经服务访问，不直接竞争裸数据库；EGM revision 不是 Aftercare fencing，旧 Worker 是否仍有业务执行权必须由网关核验。详细边界见 [ADR-0001](decisions/0001-evidence-gated-memory.md)。

显式 TaskEdge 在当前代码中已有多节点环拒绝；parent_id 与事实血缘仍不能概括为完整、并发强制的 DAG 数据库。这里以源码为准，不沿用落后于实现的 README 表述。

### 15.5 Letta：要分清版本与运行时边界

Letta 提供有状态 Agent 与记忆机制。在标为 legacy 的 V1 SDK 中，memory blocks 是可持久编辑、直接进入上下文的片段；archival memory 则是按需检索的长期存储。[Letta V1 Memory Blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)、[Letta V1 Archival Memory](https://docs.letta.com/v1-sdk/memory/archival-memory)

当前 Agent SDK 文档还描述了以 Git 支撑的 MemFS，system/ 中的内容与按需读取的文件有不同使用方式。不能把这些版本的接口混写成一套可以随意拼接的 API。[Letta Agent SDK Memory](https://docs.letta.com/agent-sdk/memory)

这里需要作出的架构决定是：究竟采用 Letta 作为有状态 Agent 运行时的一部分，还是由自己的 Harness 掌握执行，再接入一个边界清晰的记忆服务。

如果已有一套 Run、检查点与审批系统，又引入另一套可以自行推进同一业务动作的 Agent 状态机，就要特别注意状态所有权冲突。不能简单理解成“装上一个记忆包，所有恢复问题就解决了”。

### 15.6 “腾讯 Agent Memory”在本文按哪个项目理解

本文所说的腾讯 Agent Memory，按最直接匹配的官方项目 TencentCloud/TencentDB-Agent-Memory 理解；它不是泛指腾讯所有知识库或 Agent 产品。[TencentDB Agent Memory 仓库](https://github.com/TencentCloud/TencentDB-Agent-Memory)

其 MemoryCore 使用从原始对话、原子记忆、场景记忆到核心画像的分层组织。当前文档中的抽取与归纳需要 LLM API，所以“接入记忆”本身也可能产生额外延迟、成本与数据出网，需要纳入预算和权限设计。[MemoryCore 说明](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/MemoryCore/README_CN.md)

这些层级是在管理派生信息，不是决定哪个 Worker 可以领取工单，也不会自动为外部操作提供事务语义。

### 15.7 售后长期记忆应该怎样使用

适合优先记住的，是具有明确来源、相对稳定且可验证的信息：买家的语言偏好、商家已审核的沟通要求、某类问题的有效调查路径。

不适合不加判断地记住的，是未经核实的客户指令、临时物流状态、一次性审批，以及模型自行总结出的“通用退款规则”。

建议每条记忆附带主体范围、来源引用、生成时间、有效期或失效条件、版本与审核状态。检索前应用租户和访问权限过滤，不能先从所有商家的数据中做相似搜索，再希望模型自行忽略不该看的结果。

“上次经理批准了退款”只能作为历史背景，本次提交仍需新的有效授权。客户在邮件中写入“以后都给我退款”，也不能通过记忆抽取升级成系统规则。

跨租户共享经验应使用经过审核和脱敏的知识，不共享客户级原始对话、凭证或完整案件资料。删除与保留策略要考虑原文、向量、摘要和缓存之间的派生关系。

### 15.8 本项目不必同时引入多套记忆平台

可以先保存受控的商家配置、工单证据与人工确认的案件摘要，测量这些信息是否真的改善回答与执行。

EGM 已有 CandidateAtom 与来源片段校验，适合验证有限的经验候选晋升；但哈希与调用方填写的 confidence 不是自动的真实性证明。Letta 与 TencentDB Agent Memory 保留为需要长期上下文或团队经验时的参考，不因采用 EGM 就立即叠加另外两套运行时。

出现明确需求后再引入更复杂的记忆组织。例如重复工单调查成本很高、上下文维护已成为瓶颈，或者需要管理可审核的团队经验。

评价记忆效果不能只看“模型记住了多少”。应该同时看信息是否正确、是否过时、能否引用来源，以及是否引入跨租户泄露或错误规则。

## 16. Responses 还是 Messages？先纠正一个很流行的二分法

一种常见说法是：

> Responses 适合把 Agent 做成平台托管的执行流；Messages 适合把 Agent 做成应用层可控的状态机。

这句话可以表达某些开发体验上的倾向，但不能作为严格架构结论，更不能据此判断企业审计能力。

更准确的结论是：

**Responses 和 Messages 都能支持应用控制的工具循环，也都存在由供应商执行的工具能力。业务状态、审批和恢复由谁掌握，主要取决于你的架构与所选功能，而不是 URL 中写着 responses 还是 messages。**

### 16.1 两者都是结构化协议

OpenAI Responses 将结果组织成带类型的 output items。自定义工具请求通常表现为 function_call，其中包含名称、调用标识和编码后的参数；应用执行自己的工具之后，用关联的 function_call_output 返回结果。[OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling)

Anthropic Messages 的 assistant.content 也不是只能解析自然语言。tool_use 块带有 id、name 和结构化 input；应用执行客户端工具之后，把关联的 tool_result 块放在后续 user 消息中。[Anthropic 工具调用处理](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

这里 user 是协议承载角色，不表示工具结果是人类手动输入的。

| 对比项 | Responses | Messages |
|---|---|---|
| 常见接口 | /v1/responses | /v1/messages |
| 一般结果组织 | 带类型的 output items | 带类型的 content blocks |
| 自定义工具请求 | function_call | tool_use |
| 客户端工具结果 | function_call_output，关联 call_id | tool_result，关联 tool_use_id |
| 工具参数处理 | 按规定字段解析 JSON 并验证 | 读取结构化 input 并验证 |
| 应用是否能自行执行工具 | 可以 | 可以 |

所以，“Responses 是结构化事件，Messages 要从半结构化文本中猜工具调用”是不成立的。

两者都需要 Schema 校验、权限校验、错误处理和对工具调用标识的正确关联。模型生成了结构化参数，不代表参数对应的业务动作就是合法的。

### 16.2 output item 与流式事件也不是同一个概念

Responses 的流式模式会发送带类型的增量事件；Messages 同样有消息与内容块开始、增量和结束等流式事件。[Responses Streaming](https://developers.openai.com/api/docs/guides/streaming-responses)、[Messages Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)

它们可以帮助 UI 尽早显示进度，但增量参数可能尚不完整。对本案例中的业务工具，应等到请求完整、结束状态允许、参数校验与策略检查通过后再执行。

不要在看到“refund”字样或半段 JSON 时，就开始执行退款。也不要把生成中断、长度截断或部分参数错误，当成一个已经完整授权的工具调用。

### 16.3 谁执行工具，要逐个工具看

两家协议都需要区分客户端工具与服务器端工具。

自己定义的查询订单、提交工单等工具，一般由应用执行。供应商托管的搜索、文件处理或代码执行能力，则根据对应产品契约在供应商侧执行。

在 Responses 中看到 web_search_call，不意味着你的应用要再启动一次搜索来“完成这个调用”；那可能是在报告供应商托管搜索的执行信息。

Anthropic 也明确区分客户端工具和服务器端工具，不能把 Messages 概括成“供应商只回消息，所有工具循环都只能在自己服务器上”。[Anthropic Tool Use 工作方式](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)

是否使用服务器端工具，是控制权与部署边界的具体取舍。它可能减少应用维护工作，但也带来相应的数据处理、权限、可观测性和可复现性问题。不是好坏标签，而是需要逐项审查的接口契约。

### 16.4 Responses 也能由应用维护状态

Responses 可以由应用自行管理上下文，而不是必须把对话控制权交给平台。也可以选择使用 previous_response_id 或 Conversations 等提供的上下文机制。[OpenAI Conversation State](https://developers.openai.com/api/docs/guides/conversation-state)

即使选择自行保存历史，也应保留协议要求的完整相关输出项，包括适用时的推理相关或加密项，而不是只保存用户看到的文字。

但无论采用哪种方式，供应商保存的会话都不替代本文的 Case、Action Ledger、审批与 Outbox。

store:false 也不能被单独解释为“没有数据出网”或“自动满足企业全部零保留要求”。请求仍然发送给供应商，实际数据处理与保留应按所选功能、账户设置和合同核查。

Responses 的 background 模式可以把长模型请求变成异步响应与后续查询，但它管理的是那次模型生成，不是整个售后工单的持久执行。不同模式的保留与恢复条件应以当前文档和项目配置为准。[OpenAI Background Mode](https://developers.openai.com/api/docs/guides/background)

类似地，API 返回生成完成，并不等于企业动作全部完成。无论 response 完成还是 assistant 结束这一轮，工单是否关闭，都应由业务条件决定。

### 16.5 这篇文章究竟建议使用什么

为了让后续参考实现有明确起点，如果企业已经确定使用 OpenAI 模型，本文建议从 **Responses + 应用自管业务状态 + 自定义业务工具由受控网关执行** 开始。

理由是可以直接使用其结构化工具接口和流式能力，并明确控制哪些工具由自己执行；不是因为 Responses 比 Messages 更能审计，也不是因为它自动提供了企业工作流。

如果企业在售后任务集上的评测显示 Anthropic 模型效果、成本、稳定性或合同条件更合适，采用 Messages 也不需要推翻本文的业务状态、租约与沙箱设计。

模型供应商选择应使用实际任务集比较：

| 维度 | 应怎样验证 |
|---|---|
| 业务质量 | 多语言理解、证据引用、矛盾识别、该转人工时是否转人工 |
| 工具可靠性 | 参数正确率、错误工具选择、并行依赖处理、异常结果理解 |
| 安全边界 | 不可信附件中的指令是否诱发越权动作 |
| 运行表现 | 在目标负载下的延迟、限流、超时与恢复能力 |
| 成本 | 每张有效处理工单的总成本，包含重试、记忆抽取与人工复核 |
| 企业约束 | 数据处理地区、保留策略、访问控制、供应商合同 |

不要仅用“模型答得漂亮”或一次演示成功作为模型选型依据。

适配层可以把工具意图映射成内部结构，但仍要保存供应商特有的协议数据。一个统一的 ToolIntent 并不能无损表达两家所有上下文、推理和服务器工具状态。

跨供应商故障切换，更可靠的起点是已经核验的业务检查点与工具结果，而不是把一家的原始消息数组原封不动塞给另一家；切换也不能重做已经发生的外部操作。

## 17. 这和 Grok Bot 有什么区别？

本节讨论的对象是 Grok Bot 产品，不是泛指 Grok 模型 API，也不是 X 上的 @grok 账号。

截至本文核查日期，Grok Bot 的详细企业架构文档描述：它在 Cursor 云上运行，每个用户拥有一台持久 Firecracker microVM，同一用户的多个 Bot 共用这台电脑。[Grok Bot 企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)

安全文档还说明当前仅支持其托管环境，不支持客户本地机房部署、放入客户自己的边界或自带镜像。不能从其他产品的自托能力推导 Grok Bot 也具备相同交付方式。[Grok Bot Security](https://docs.x.ai/grok-bot/security)

需要注意，部分发布介绍中的“每个 Bot 有自己的电脑”措辞，与详细架构页的每用户共享描述并不完全一致。涉及隔离边界，本文采用详细架构与安全文档的口径，并保留核查日期。[Grok Bot 企业发布介绍](https://x.ai/news/grok-bot-for-enterprise)

这并不意味着我们已经知道它内部每个模型循环、规划器和状态服务分别在哪个进程里运行。公开执行环境资料不足以证明它属于纯粹的 Harness in Sandbox，更不能据此虚构它使用了哪种消息队列或租约算法。

真正可以比较的，是资源与状态的默认归属方式：

| 维度 | Grok Bot 当前公开的工作环境 | 本文售后 Agent 参考设计 |
|---|---|---|
| 环境归属 | 以用户持久云电脑为中心 | 以租户、工单与步骤权限为中心 |
| 多个 Agent 与环境 | 同用户 Bots 共享电脑 | 依据工单与信任边界分配环境 |
| 状态复用 | 文件、登录与长期工作环境有较高价值 | 业务事实、证据、审批与操作记录优先 |
| 等待期 | 产品管理持久环境生命周期 | 长等待不要求保留活跃执行资源 |
| 核心设计关注 | 持续进行用户交付的工作 | 大量工单的公平调度、受控动作与故障恢复 |

这是产品取向与参考架构的比较，不是“个人玩具”和“企业产品”的比较。Grok Bot 本身也有企业治理能力。

两者可以共享许多基础设施思想，但不能简单地把一个人的持久工作环境复制一千份，就认为得到了正确的多租户售后平台。

## 18. 把组件串起来：一张“未收到货”工单怎样运行

以下时间和标识都是示例。

### 第一阶段：受理，而不是立即占用所有资源

买家消息进入系统。接入服务验证来源，识别租户，用来源消息 ID 做去重，在事务中创建 Case、初始 Run 和待执行记录。

提交成功后，才向接入方确认已经受理。

此时工单可以排队，不需要立即分配沙箱。客服界面看到的是可追踪的排队状态，而不是一个一直转圈、最终可能丢失的 HTTP 请求。

### 第二阶段：调查，按步骤使用资源

Worker 取得 Run 租约和 token，读取商家政策与工单信息，经过模型额度准入后请求模型。

模型提出查询订单和物流。Harness 确认两项都是获准的独立读取，再受限并行执行。

发现需要处理签收证明附件后，Sandbox Manager 从干净暖池中分配环境。系统传入这张工单需要的文件，不传入全部客户数据库。

解析结果和必要截图保存到对象存储，结果引用写回检查点。沙箱任务结束后回收资源。OTel 记录执行耗时，业务事件记录“证据已保存”，前端显示对应进度。

采用 EGM 的验证路径中，工具网关核对证据来源、运单和订单关系，再由受限 Adapter 导入。门控可以指出当前材料还不足以支持“已解决”，但不能把买家的描述或任意 API 响应直接作为已完成的证明。

### 第三阶段：缺少资料，结束本次执行片段

Agent 判断需要买家补充信息。普通询问信息通过既定策略检查与发送操作记录管理；如果企业规定此类对外消息也需人工审核，就进入相应审批。

获得所需授权后，先持久化发送意图及关联的等待信息，再执行发送。确认消息发出、准备进入等待时，核对持久 Inbox 中是否已有有效回复：如果已有，直接安排继续；如果没有，保存可恢复的等待状态与提醒时间。Worker 释放执行权，沙箱无需继续运行。

即使有三万张类似等待中的工单，系统主要承担的是持久状态和定时器管理，而不是三万套活跃浏览器。

### 第四阶段：事件恢复与人工审批

第二天买家回复。接入服务验证、去重，并匹配尚未满足的等待条件。系统创建或恢复一个允许推进的执行片段。

Worker 重新读取订单状态与政策，不能只信任昨天的记忆摘要。

Agent 形成一个补发建议，业务系统生成固定参数的 Action，等待有权限的人员审批。客服批准的是具体订单、收件对象和补发内容，而不是给 Agent 一张无限期通行证。

### 第五阶段：工具成功后崩溃

提交补发之前，操作台账已写入 DISPATCHING，且具有稳定幂等键。

订单系统接受请求，但 Worker 在保存回执前崩溃。租约随后到期，新 Worker 接管。

新 Worker 看到的不是“失败了，所以重新补发”，而是“这个动作可能已经发生”。它按目标系统能力查询操作结果，或者使用原幂等键按契约恢复请求。

取得回执后，系统把 Action 更新为 CONFIRMED，并持久化工单状态变化与后续通知任务。

核验后的回执随后可成为 EGM 中的支持证据。顺序不能颠倒为“EGM 接受了完成结论，所以把未知操作标记成功”；EGM 导入失败也不能反向抹去已经确认的外部动作。

如果始终无法确认，就进入 UNKNOWN 的对账或人工处理分支。模型不能靠猜测宣布成功。

这张工单的企业级能力，不是来自某个神奇 Prompt，而是来自接入持久化、执行权管理、受控工具和恢复规则的共同作用。

## 19. 从 Demo 演进时，按什么顺序实现

下面是一条演进路线，不要求在第一天全部做完。

| 阶段 | 主要目标 | 核心模块 | 进入下一阶段前的验证 |
|---|---|---|---|
| V0：离线业务验证 | 证明 Agent 对售后调查有帮助 | 脱敏样本、工具模拟、评测集、受限 EGM PoC | 证据质量可量化；错误回执和越界记忆被阻止 |
| V1：单 Worker 持久运行 | 服务重启后任务可恢复 | PostgreSQL 状态、检查点、Action、持久等待 | 重启不丢任务，不盲目重做副作用 |
| V2：多 Worker | 控制执行权与多租户并发 | 租约、fencing、版本校验、配额、Outbox | 重复事件、旧 Worker、同订单竞争下行为正确 |
| V3：按需沙箱 | 安全运行浏览器和代码工具 | Sandbox Adapter、权限出口、产物存储 | 租户隔离、出网限制、回收与重建有效 |
| V4：容量优化 | 降低排队与冷启动成本 | 暖池、分层伸缩、背压、限流观测 | 在目标负载与故障下满足定义好的指标 |
| V5：按需求扩展 | 接入更多系统和经验管理 | 可选 Broker、ACP、记忆平台 | 每个新增组件解决了已测量的问题 |

安全、权限和必要审计不是到后面才补的功能；表中的阶段表示能力演进，不表示前期可以直接开放危险操作。

模块组织可以先保持在一套代码库中：

~~~text
case-api          接入、身份、工单与审批接口
runtime           Harness、检查点、状态转换与恢复
scheduler         任务领取、等待、配额与公平调度
model-adapters    Responses / Messages 协议适配
tool-gateway      工具权限、Action 与外部回执
sandbox-adapter   环境申请、执行、产物与回收
event-projection  业务事件、前端订阅、可选 ACP
evidence-adapter  EGM 接入、来源与业务绑定、解释投影及版本
memory-adapter    受权限约束的长期记忆读写（按需）
observability     指标、追踪、脱敏与运行诊断
~~~

这是一种职责划分，不是必须创建九个微服务。先把边界写清楚，比先把网络调用数量做大更重要。

## 20. 怎样证明它真的接近企业级，而不只是架构图好看

需要同时做业务评测、容量测试和故障注入。本文没有执行这些测试，因此下面是验收方案，不是测试通过声明。

### 20.1 故障注入清单

| 注入点 | 期望看到的行为 |
|---|---|
| 接入提交后、响应发送前断开 | 来源重投不产生重复业务工单 |
| Worker 领取后崩溃 | 租约到期后可接管，已保存状态不丢失 |
| 旧 Worker 在接管后恢复 | 旧版本写入被拒绝，外部动作仍受操作台账约束 |
| 工具成功但回执尚未持久化 | 进入查询或 UNKNOWN，不生成新幂等键盲目重试 |
| Outbox 已发消息但未记为已发送 | 重投不会重复推进相同业务效果 |
| 买家回复与超时同时到达 | 只有仍有效的等待条件可以推进流程 |
| 回复先于等待条件提交到达 | 回复先持久保存，登记等待后可匹配，不永久漏唤醒 |
| 同一订单出现两个并行 Run | 关键动作受订单级业务约束与版本保护 |
| 模型持续返回 429 | 有界退避、预算与背压生效，不形成重试风暴 |
| 模型产生截断或非法工具参数 | 不执行半成品动作，记录明确失败原因 |
| 沙箱 OOM、失联或回收失败 | 不误报业务成功，必要时重建环境并核对状态 |
| 恶意附件要求读取其他租户数据 | 权限层拒绝，敏感信息不会仅靠 Prompt 保护 |
| 暖池耗尽 | 排队与超时可解释，不绕过容量上限 |
| 记忆中出现过期规则 | 权威政策覆盖派生记忆，不产生越权动作 |
| EGM 收到失败回执或另一订单回执 | 业务校验器拒绝生成成功证据，不能仅因类型齐全而放行 |
| EGM 投影滞后、导入中断或旧写者恢复 | 不依据过时 accepted 结果推进危险动作；可从权威记录恢复 |
| 客服断线或重复点击批准 | UI 可恢复，审批与动作不因重复点击重复提交 |

还应实际演练数据库备份恢复、消息保留与积压恢复、凭证轮换、取消和人工接管。只验证“Worker 重启后还会输出文字”远远不够。

### 20.2 容量测试要区分几个负载形态

至少分别测试：持续稳定流量、短时间突发、外部系统变慢、模型限流、长时间等待后集中唤醒，以及某个大租户占据多数流量。

记录的指标包括排队时长、执行片段耗时、端到端工单时长、模型与工具错误率、沙箱申请时延、暖池命中率、未知操作数量、人工接管率和单工单总成本。

人工等待不宜混进同一个“模型处理耗时”指标，否则优化 API 延迟可能看起来对工单总时间毫无作用，却掩盖了真正的执行效率变化。

业务正确性同样需要分层：任务被受理、流程执行结束、建议被人工接受、外部动作已确认、售后问题真正解决，是不同的成功口径。

### 20.3 用消融和敏感性分析替代手填分数的自我证明

消融实验，也就是 ablation，可以回答：“拿掉这个组件之后，结果会怎样？”

例如，在同一套售后样本与相近实验条件下，关闭长期记忆，比较调查质量与成本；关闭暖池，比较启动延迟与闲置资源成本；把并行读取改成串行，测量延迟变化。

敏感性分析，也就是 sensitivity analysis，回答：“参数改变时，结果如何变化？”

例如逐步改变每租户并发额度、暖池大小、最大步骤数或重试预算，观察吞吐、尾延迟、失败率与成本的变化。

这两类实验不意味着可以在生产中关闭权限、审批或隔离来追求速度。涉及安全控制的对照应在隔离测试环境中进行，使用合成或获准的脱敏数据。

如果一个复杂组件没有改善已定义的指标，反而增加恢复和运维难度，就应该重新考虑它。企业级能力应该由测量和故障行为证明，而不是由默认参数的精确小数位证明。

## 结语：企业级 Agent，是受业务约束的可恢复执行系统

本文的起点选择可以压缩成几句话：

让模型负责理解不规则信息和提出下一步；让业务代码掌握权限、金额与状态转换；让 Harness 协调模型与工具；让持久化层保存可恢复的事实；让沙箱隔离有风险的执行；让调度系统按资源限制管理并发。

从 PostgreSQL 和明确的状态机开始，在业务需要时引入 E2B 或 Kubernetes Agent Sandbox，在确有分发与回放需求时引入独立持久消息系统。ACP 用于需要兼容的客户端交互，OTel 用于诊断，记忆系统用于经过权限约束的派生知识；它们不互相替代。

EGM 为这套设计补上一个值得验证的证据准入层：它可以组织支持关系、校验声明的回执契约、发现缺项和追踪失效，但业务真值、授权和工作流恢复责任仍留在 Aftercare。已有服务化源码不等于已完成整个企业平台；先以离线 Adapter 与影子运行验证价值，再决定多机存储与容量演进。

最重要的分界线，不是“用了哪家模型”，也不是“有没有 Kubernetes”。

**而是当同一张工单被重复投递、执行机器失联、外部工具结果未知时，系统还能否说清楚：现在发生了什么，谁可以继续，下一步怎样做才不会伤害业务。**
