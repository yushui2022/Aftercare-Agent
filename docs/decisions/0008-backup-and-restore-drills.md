# ADR-0008：备份、恢复演练、保留删除与恢复后的外部动作核对

状态：接受，D-02 实施中。本 ADR 决定"什么算恢复能力"，以及为此新增的 `aftercare-backup`
的边界。它不替代任何既有决策：ADR-0002 的嵌入式 EGM、ADR-0003/0004/0005 的授权边界、
ADR-0006 的连接池语义与 ADR-0007 的池指标/容量口径继续有效。

## 背景

D-02 要求 PostgreSQL/对象备份恢复、保留删除、RPO/RTO 与版本升级，验收写明是"实际恢复
演练、恢复点之后外部动作核对"，并且明确"不是只检查备份任务显示成功"。在这个 ADR 之前，
仓库里没有任何备份或恢复代码：`backup|restore|pg_dump|retention` 只出现在路线图、技术栈
和 Compose 说明的待办句里，RPO/RTO 一直是开放项。

## 决策

1. **一次备份 = 一份 dump + 一份清单，两者来自同一个快照。** 清单记录恢复点时间、数据库
   名与服务端版本、schema 版本、每一条迁移的 SHA-256、每张 `aftercare_` 表的行数、dump
   的字节数与 SHA-256、生成 dump 的客户端版本。只有 dump 的话，"恢复出来的库对不对"没有
   可比对的答案；`verify` 与 `drill` 都是拿清单当预期值。
2. **一致读靠 PostgreSQL 自己的机制。** 备份在一个 `REPEATABLE READ` 事务里
   `pg_export_snapshot()`，先用这个快照读 schema 与行数，再把同一个快照交给
   `pg_dump --snapshot`，dump 完成后才提交。行数与 dump 由此描述同一时刻的数据，
   "恢复后行数相同"才是判定而不是近似。这**不是**给业务事务加长事务：它是运维工具的一次
   只读快照，不持有应用表锁，也不进请求路径。
3. **判据是演练，不是退出码。** `drill` 把 dump 恢复到一个刚建出来的临时库
   （`CREATE DATABASE ... TEMPLATE template0`，`pg_restore --single-transaction
   --exit-on-error`），然后逐条比对迁移集合的摘要、`aftercare_` 表集合与每张表的行数，
   最后删掉临时库。备份任务返回 0、文件存在、大小合理都不是验收证据。
4. **临时库绝不误用。** 名字默认由时间戳生成并限制为普通标识符；目标库已存在时默认拒绝，
   要用 `--replace-scratch` 显式覆盖；`--keep-scratch` 只用于人工排查，且是调用者的选择，
   不计为失败；清理失败不会掩盖导致失败的原始异常。
5. **RPO 不由演练发明。** 演练只证明"这份 dump 代表哪个恢复点"，以及在这台机器上恢复它
   用了多久（RTO = restore + verify + upgrade）。RPO 是备份**节奏**的属性，必须在有目标的
   部署上按节奏与本 ADR 的演练一起给出；本机单次演练不能替代。
6. **保留删除先出计划再执行，且永不删空。** `retention` 默认先打印"保留谁、删谁、为什么"
   的计划；`--apply` 才真的删除，并且始终保留最新 `keep_last` 份，之后每个自然日（UTC）
   再保留一份，最多 `keep_daily` 天。任何会删空的计划都被拒绝；名字必须匹配受限模式，
   防止清单里的路径把删除引到备份目录之外。
7. **恢复点之后的外部动作单独核对。** 恢复数据库回滚的是动作的**记录**，不是动作本身。
   `reconcile` 从 `aftercare_actions` 里列出两类 Action：任何 `UNKNOWN`（持久结局，与恢复
   点无关，必须按同一个 Action 与供应商核对），以及 `updated_at` 晚于分界线的行（它们可能
   已经不在恢复副本里）。分界线默认比恢复点**再提前 60 s**（`--safety-margin-seconds`）：
   与 dump 赛跑的那个提交可能在内也可能在外，把窗口放宽一分钟只花人工时间，收窄则可能
   重复一次真实外部动作。工具不调用供应商、不解析结果、不自动改状态。
8. **升级演练在真实数据上跑。** `drill --upgrade` 在恢复出来的副本上执行
   `migrate()`，报告应用了哪些版本，并再次比对行数，证明迁移没有吃掉数据。由本 build 生成
   的备份本来就在本 build 的 schema 上，所以这条路径通常应用 0 个迁移；真正跨版本升级需要
   一份在迁移之前生成的 dump，只有同时拥有新旧版本的部署才能提供。
9. **工具不碰模型、供应商与运行时。** 它只用 psycopg 与 `pg_dump`/`pg_restore`，不 import
   请求路径上的模块，不做真实业务动作；密码只经 `PGPASSWORD` 传给子进程，不出现在命令行。
10. **客户端版本不匹配要提前失败。** `pg_dump` 拒绝读取比自己新的服务端，因此工具在动
    dump 文件之前先解析 `pg_dump --version` 的 major 与服务端 `server_version`，不匹配就
    给出可操作的报错。这是 CI 里 `postgres:17` 服务与 runner 自带旧客户端冲突的原因，
    处理方式见 [运维文档](../operations/backup-restore.md)。

## 本机实测（2026-09-15，临时真实 PostgreSQL 16.13，CPython 3.13.15）

数据取自本机临时集群上一次完整演练，报告原文见
[`2026-09-15-restore-drill.json`](../operations/2026-09-15-restore-drill.json)。

| 项目 | 数值 |
|---|---|
| dump | 111,950 字节（custom 格式），判据来自 31 张 `aftercare_` 表 |
| 恢复点 | 2026-09-15T12:07:29.551463Z；演练开始时距恢复点 5.8 s |
| 恢复 (pg_restore) | 0.703 s |
| 比对（迁移/表/行数） | 0.158 s |
| 升级 (migrate) | 0.151 s |
| RTO | 1.012 s（restore + verify + upgrade，同一台机器、同一个 dump） |
| 比对结果 | 31 张表全部还原、行数完全一致、迁移摘要一致、升级后行数不变 |
| 核对清单 | 同一库上 7 个 Action 需要复核：2 个 `UNKNOWN`、5 个在上次恢复点之后被更新过 |

**这些数字只说明方法与口径，不是 SLA。** 备份大小、表数与耗时都依赖具体数据库；换机器、
换 PostgreSQL 版本、换数据量都要重跑。

## 后果

- 运维多了一个入口 `aftercare-backup`（`create`/`verify`/`drill`/`retention`/`reconcile`），
  退出码 0 = 通过、1 = 检查未通过、2 = 缺参数或环境不允许。
- 备份目录多一类文件：`<name>.dump` 与 `<name>.manifest.json`，两者必须成对保留，
  保留策略按清单里的 `taken_at` 判断。
- `db.py` 多了 `known_migrations()`/`latest_schema_version()`：迁移清单的 SHA-256 只有一份
  定义，`migrate()`、`verify` 与 `drill` 用的是同一份。
- 演练会短暂占用一个临时数据库，并在同一实例上做一次全量恢复；容量紧张的实例要把这台
  机器算进去。
- 仍未完成：WAL 归档/时间点恢复（PITR）、对象存储与异地副本、备份加密与密钥托管、
  自动化的定期演练与告警、按目标的 RPO/RTO 结论、多租户级选择性恢复。本 ADR 只固定
  "一次备份怎么算数"，不宣布 D-02 整体完成。
