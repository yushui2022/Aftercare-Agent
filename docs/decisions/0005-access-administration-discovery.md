# ADR-0005：访问管理员的租户工单发现

状态：接受，D-01-07 实施中。真实 IdP 权限映射与演练、RLS、租户级授权总览和生产审计
留存仍不在本 ADR 范围内。

本 ADR 细化 [ADR-0004](0004-case-grant-administration.md) 决策第 2 条（管理权是租户级
角色），不替代任何既有决策：ADR-0003 的“CaseGrant 是访问权威”与 ADR-0004 的闭集、
委派上限、乐观并发继续有效。它补充的是 ADR-0004 没有回答的问题——一个租户级管理角色，
如何知道租户里存在哪些 Case。

## 背景

ADR-0004 让移交成为可能，但漏掉了它的前置条件：移交要先能**命名**目标 Case。`GET /v1/cases`
是数据面入口，每一行都来自活动 `CaseGrant`（`list_accessible`），于是一个不参与任何工单的
访问管理员打开工作台看到的是空队列——它手上明明有 `grant:admin`，却无法把任何一件工单交给
别人。ADR-0004 决策第 2 条明确要求管理动作**不**解析调用者自己的 CaseGrant，理由正是
“第一条授权就永远发不出去”；同一条理由适用于发现：要求先持有 grant 才能看到工单，等于
要求先被授权才能授权。

反方向的诱惑是把 `grant:read` 加进工单列表的判定，让管理员的队列显示租户全部工单。这等于
顺手放宽数据面：`GET /v1/cases/{case_id}`、Run、Review、Approval 与事件流用的是同一套
授权判定，一旦租户级 scope 能打开 Case 内容，`grant:read` 就变成“租户管理员对所有客户数据
的常驻读权”，与逐工单 grant 收敛权限的立场相反。

## 决策

1. 新增控制面入口 `GET /v1/administration/cases`，需要租户级 `grant:read`，沿用数据面工单
   列表的同一套 keyset 游标参数（`status`、`limit`、`after_created_at`、`after_case_id`）
   与 `next_created_at`/`next_case_id` 响应契约。
2. 该页面只返回标识与进度：`case_id`、`order_id`、`status`、`version`、`created_at`。
   Case 内容、Run、Review、Approval 与事件流仍然逐工单判定 `CaseGrant`，`grant:read`
   不参与它们的授权判定，因此数据面没有放宽。
3. 页面行的 `permissions` 只报调用者自己的租户级管理 scope（新增闭集
   `ADMINISTRATION_PERMISSIONS = {grant:read, grant:admin}`），**绝不**复用逐 Case 投影。
   该集合与 `GRANTABLE_CASE_PERMISSIONS` 分开维护：后者界定“一张 Case 行允许授出什么”，
   前者界定“一行租户清单允许声明什么”。混用会让控制面清单声称调用者并不具备的内容权限，
   而工作台正是拿这个字段决定要不要调用内容路由。
4. 该入口不解析任何 `case_id` 参数，因此没有“单资源存在性”可言：它只返回调用者自己租户的
   清单。跨租户与未知 Case 的不可区分语义（ADR-0004 决策第 2 条）继续由单资源路由承担。
5. `CaseRepository.list_for_tenant()` 的合法调用者从“仅显式启用的合成身份”扩为两类，并写进
   docstring：合成身份的 scope 就是租户；持 `grant:read` 的访问管理员用它完成发现。该读取
   仍接受 `case_ids` 作为 token 上界且只收窄——真实 operator 队列继续必须走
   `list_accessible`。
6. 单工单授权台账响应新增两个字段：`delegable`（闭集内调用者可授出的权限）与
   `can_administer`。二者描述的是**调用者而不是 Case**，因为客户端无法从 Case 投影推导它们：
   投影是与 grant 的交集，一个在该 Case 上没有 grant 的租户管理员在投影里根本看不到
   `grant:admin`。服务端是唯一权威，且这两个值都是调用者自己出示的 scope，不泄漏新信息。

## 后果

访问管理员现在能完成完整交接：看到租户里有哪些工单 → 打开其中一个 → 只看到授权台账与移交
表单 → 把他人的工单移交给别的操作员。这是 ADR-0004 与本 ADR 的分工结果：ADR-0004 定义谁能
改授权，本 ADR 定义谁能看见“有哪些工单可以改”。

代价与边界：

- 租户级清单本身是元数据暴露面：`grant:read` 持有者能看到全部工单编号、订单号与状态。因此
  `grant:read` 必须只发给真正的访问管理员，不能因为“只是读”就发给普通操作员或分析账号——
  与 ADR-0004 对 `grant:admin` 的要求同源。
- 工作台把清单与队列分成两块：队列是数据面（每行都有 grant），"本租户其他工单"是控制面
  （行内标注“仅可管理访问”）。选中控制面行时工作台不调用任何内容路由，而是显示说明加授权
  面板，避免每次点击都触发一次注定 `403` 的请求。
- 两侧分页各自独立：清单与队列的游标不共享，因为判定不同、行集合也不同；同一个 Case 可能
  同时出现在两边，此时队列行优先，因为只有它携带真正的 Case 权限。

仍未完成，因此不能据此宣称生产就绪：真实 IdP 权限映射与演练、RLS、跨工单的租户级授权总览
（“谁对这个租户的哪些工单有权限”）、以及管理动作的生产审计留存。
