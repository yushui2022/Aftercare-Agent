# ADR-0006：按测量启用有界连接池，其余扩展组件保留为候选

状态：接受，D-04 实施中。本 ADR 只决定“启用连接池”，并明确 Broker、暖池、ACP、长期记忆
与额外供应商**仍未启用**。它细化[技术栈](../tech-stack.md)第 3 节的连接边界，不替代任何既有
决策：ADR-0002 的嵌入式 EGM 与 ADR-0003/0004/0005 的授权边界继续有效。

## 背景

`Database.transaction()` 原本为每个工作单元调用一次 `psycopg.connect()`。本机实测建连
p50 115.2 ms / 最大 215.3 ms，而同一测量里一次续期事务 p50 0.8 ms；同一套用例在本机 79.0 s、
在 CI Linux 14.7 s。差距不在断言或 SQL，而在每个工作单元都要付一次 TCP 与认证握手。

这不是理论问题。A2-02 之前把建连放进了租约的截止预算：200 ms 租约 + 30 ms 间隔下单 tick 只剩
约 133 ms，本机连续单跑 20 次失败 11 次；修法是让心跳线程独占一条连接。`PostgresEventTail`
每轮轮询同样走一次 `transaction()`，300 ms 尾部窗口在慢建连主机上会漏事件（观察到 1 次，
隔离对照两次各 8/8 通过，没有稳定复现，但机制明确）。两处都指向同一个结论：连接生命周期
不该和工作单元一样短。

D-04 要求“每个新增组件有需要、方案、代价、迁移和验收，未启用项明确保留为候选”。本 ADR 就是
对这条要求的回答，而不是一次性把所有候选都接上。

## 决策

1. **启用 psycopg_pool（锁定 3.3.1，随 psycopg 3.3.5，LGPL-3.0-only，与已在用的 psycopg 同
   一许可）**。技术栈第 2 节本来就写着“psycopg 3 + psycopg_pool”，本 ADR 是把这句话变成事实，
   不是新增承诺。
2. **`Database` 默认带池，`Database.direct()` 保留无池模式**。默认 `min_size=1`、
   `max_size=8`、`acquire_timeout=5 s`，可由 `AFTERCARE_DB_POOL_MIN_SIZE`、
   `AFTERCARE_DB_POOL_MAX_SIZE`、`AFTERCARE_DB_ACQUIRE_TIMEOUT_SECONDS` 覆盖，显式构造参数
   优先于环境变量。池在第一次借用或 `startup()` 时才打开，构造 `Database` 不产生线程和连接。
3. **池必须有界、有等待上限、失败 fail-closed**。在 `acquire_timeout` 内拿不到连接就抛
   `ContractViolation(RETRYABLE)`（HTTP 503），不退化成无限等待；等待中的工作不占连接，
   只占一个线程（系统设计“不能为几千个等待工单一直保留几千条连接”）。`startup()` 预热
   `min_size` 并在数据库不可达时让进程启动失败——迁移本来就会失败，缺连接不该等到第一个请求
   才发现。
4. **借还语义不变**。仍按工作单元借还、短事务、事务内不做网络调用、不在线程之间共享**正在
   使用**的连接。池化的新增事实是：同一条连接会在两次借用之间换线程，而池只回滚“归还时未
   结束的事务”，**不重置会话状态**，因此池化连接上不得留下 `SET`、`LISTEN` 或 `search_path`
   （`SET LOCAL` 随事务回滚，仍然可以）。当前仓库没有任何这类语句，这条不变量写进了 `db.py`
   的 `open()` docstring。
5. **长持有者改用 `open()`/`release()`**。租约心跳仍跨多个短事务独占一条连接，只是从“自己
   建、自己关”改成“从池借、用完归还”，并且仍占一个槽——这正是 `max_size` 默认高于
   `min_size` 的原因：单进程的 Worker 同时需要“心跳占 1 条 + 切片当前用 1 条”。
6. **借用前做一次健康检查**（`check=ConnectionPool.check_connection`）。实测本机 0.09 ms/次
   （0.36 → 0.45 ms/次借用），换来的是数据库重启后丢弃坏连接，而不是让一个工作单元失败。
7. **不改事务边界去换性能**：不引入跨请求的长事务、不在池层做自动重试、不把 Repository 改成
   持有连接。性能来自连接复用，不来自放宽正确性。

### 本轮明确不启用，保留为候选

- **Broker（Kafka/NATS）**：现有 outbox 与 `PostgresEventTail` 已满足“已提交事件不丢、可重放、
  重复消费安全”的既有验收，且不需要第二个持久层与数据库一致性对齐。触发条件：D-03 压测显示
  outbox 轮询/投递成为瓶颈，或出现跨服务分发需求。
- **暖池（独立预热进程/池）**：连接池的 `min_size` 预热与 `startup()` 已覆盖这个需求，再引入
  第二个预热机制只会重复计费。触发条件：D-03 显示稳态连接数远高于活跃并发。
- **ACP**：属于可选互操作面，没有已确认的对端与协议范围，不是运行必需。
- **长期记忆平台**：EGM 证据记忆已经是记忆边界（ADR-0001/0002），再引入一个记忆平台会分裂
  “哪份证据权威”。触发条件：出现 EGM 明确不覆盖、且无法用同一证据模型表达的需求。
- **额外供应商（模型/通知/对象存储）**：阶段 A 只生成草稿、不真实外发；模型走 Fake 与适配器，
  供应商与驻留约束本来就是 B/C 阶段的前置条件，不是连接层问题。

## 后果

已实测的行为变化（本机、临时真实 PostgreSQL、每次重建空库）：

- 25 个连续事务只落到 **1 条物理连接**；稳态 **0.47 ms/事务**，对照 `direct()` 的
  **114.8 ms/事务**（每个事务一条新连接）。
- 同一批 **509 个既有用例：79.0 s → 30.4 s**（同一台机器、各跑一次）。
- `PostgresEventTail` 每轮轮询不再付建连：轮询复用的后端数有独立回归用例固定。

代价与边界：

- 每个进程多一个池和它的维护线程；池规模必须按**并发**而不是按队列长度估算。
- 连接归还走池的后台任务，“归还”与“下一个借用者拿到它”之间多一次调度；借用者拿不到时会等待，
  或在超时后 fail-closed。
- 池不隔离会话状态（见决策 4），这是把 `SET`/`LISTEN` 排除在池化连接之外的代价。
- `max_size` 目前是默认值而不是压测结论：D-03 的稳态/突发/集中唤醒压测要给出每进程的定标
  依据，本 ADR 只保证“有界 + 超时 + 可配置”。
- 池指标（等待数、超时数、连接数）还没有接进观测，目前只能用日志与数据库侧会话数观察。
- EGM 仍可能是同一 PostgreSQL 的另一个客户端：同事务写入必须沿用同一个连接与外层事务，
  池不会让它“看似同库”地另开一个连接。

仍未完成，因此不能据此宣称生产就绪：D-03 的容量定标与池指标接入、D-02 的备份恢复演练，
以及本 ADR 列出的候选组件的触发条件验证。
